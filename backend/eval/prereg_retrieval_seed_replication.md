## 4. 予測と比較の定義

### 4.1 比較の単位と定義

- **検索の行**: （質問, 条件）の組。14問×4条件で56行。
- **順位リストの一致**: 起点を除いた上位10件の科目コードの列（`ranked[].code`）が、順序も含めて完全に一致すること。
- **スコアの差**: 同じ行の同じ順位の `score` の差の絶対値の最大。順位リストが一致しない行では、同じ科目コードどうしで比べる。
  C1・C2 はコサイン類似度、C3 はグラフ探索の返す値、C4 は RRF の値。
- **指標の一致**: 行ごとの `scores`（K=5・10 の Recall・NDCG・forbidden・前提違反ほか）が完全に一致すること。
- **埋め込みの差**: 同じテキスト（科目コード・質問 ID で対応づける）の元と再現のベクトルについて、要素ごとの差の絶対値の最大と、
  コサイン類似度（保存前に L2 正規化しているので内積）を求め、34本（文書20・質問14）の最大と最小を出す。
  「ビット一致」は pgvector のテキスト表現（`embedding::text`）が34本すべてで一致すること。
  「ほぼ一致」はビット一致ではないが、34本すべてでコサイン類似度が 0.9999 以上のこと。
- **生成**: 生成は同じ入力でも揺れるので、回答文は比べない。条件ごとの集計（成功数、未検証コードの合計、
  候補外の引用の合計とそのうち根拠文に現れる数、recall・precision の平均、forbidden の合計）を並べ、違いは記述だけにする。
  あわせて、（質問, 条件）ごとに起点を除いた引用の集合が元と一致した数（40行中）を出す。
- **仮説の判定**: 元の登録 §6 の H0〜H7 を、同じ関数（`retrieval_metrics.evaluate_hypotheses`）で両方の記録に適用し、ラベルを並べる。
- 所要時間は環境で変わるので判定に使わず、記述だけにする。

### 4.2 予測

- P1（R1）: 56行すべてで順位リスト・スコア・指標・evidence・DB クエリ数が元と一致する（スコアの差の最大は 0）。
- P2（R2 のスナップショット）: PostgreSQL の20行、`seed/courses.json`、Neo4j のグラフ、QuerySpec、golden のハッシュが元と一致する。
- P3（R2 の埋め込み）: 予測はしない（API が同じ入力に同じ値を返すかは確かめていない）。ビット一致・ほぼ一致・それ以外のどれかを記録する。
- P4（R2 の検索）: C3 の14行は埋め込みに依存しないので、埋め込みの結果によらず一致する。埋め込みがビット一致かほぼ一致なら、
  56行すべてで順位リストが一致し、H0〜H6 の判定も一致する。それ以外なら予測しない。
- P5（R2 の生成）: 40回すべて成功し、未検証コード（DB に無いコード）の合計は0。候補外の引用は、あってもすべて渡した根拠文に現れるコードである。

### 4.3 結論の規則

- **元の検索の結果はコミット済みのコードで成り立つ**: P1 が成り立ち、かつ R1 と R2 の manifest の出所（HEAD、clean、ソースの指紋）が
  git の木と一致する。
- **元の結果は再現した**: 上に加えて、R2 で56行すべての順位リストが一致し、H0〜H6 の判定が一致し、P5 が成り立つ。
- どれかが成り立たなければ、違った行・指標と原因（コードか埋め込みか）を書き、再現側の値で仮説を判定し直して並べる。
  元の結果のファイルは残し、実験報告に違いを明記する。

## 5. ハーネスに足す変更（API を呼ぶ前にコミットする）

### 5.1 出所の記録

- `setup-db`・`embed-docs`・`embed-queries`・`retrieve`・`generate` に `--git-status`（ホストの `git status --porcelain` の出力）を
  必須で渡す。空でなければ実行を拒む。コンテナに `.git` が無いので、HEAD（`--git-sha`）と同じく外から渡す。
- 各セッションに、コンテナから見えた backend のソースの指紋（ファイル数と、パスと git の blob SHA-1 の一覧の SHA-256）を記録する。
  対象は backend 配下のファイルで、名前が `.` で始まる要素・`__pycache__` を含むパス、`logs/`、`eval/results/` を除く。
  blob SHA-1 は改行を LF にそろえてから計算する（Windows の checkout は CRLF なので、git の正規化に合わせる）。
- 比較スクリプトが、`git ls-tree -r <HEAD> -- backend` から同じ規則で指紋を作り、manifest の指紋と一致するかを確かめる。
- 実験用 DB のホスト名とデータベース名（パスワードは除く）もセッションに記録する。

### 5.2 予算の上限

`--llm-budget` と `--embedding-budget` を足す（既定は元の登録どおり 150 と 100）。残りは同じ manifest のセッションの
使用量から計算する（元と同じ）。指定した値はセッションに記録し、サマリーの分母にも使う。

### 5.3 比較スクリプト

`eval/replication_compare.py`。§4.1 の比較を機械的に行い、`results/2026-10-13_retrieval_seed_replication_compare.md` と
`.json` に書く。埋め込みのベクトルそのものはリポジトリに入れず、差の統計だけを残す。

## 7. 限界

- R2 は1回だけで、生成の揺れの大きさは測らない（元と再現の2回を並べるだけ）。

  「コミット済みのコードで同じ結果が出るか」までである。
