## 0. 要点

1. 回答に 1 問あたり 53〜93 秒かかる（サーバー側。10/11 の 3 問の動作確認【リポ】）。待ち時間をどう見せるか・切れたときどうするかが、技術要件の中心になる
2. 公開先の GMS サーバーは、11/3 17:06 に学外から開くと Traefik の自己署名証明書（警告が出る）で、警告を越えても `/` が 404 だった【実測】。どのホスティング案でも、ここが直らないとインタビューができない
3. 研究用のログは、今の MCP 経路では何も残らない（trace JSONL は静的経路だけ）【リポ】。参加者 ID・条件 ID 付きの記録にはバックエンドの変更が要る（数十行の見込み【推定】）
4. 開発用キーが無料枠の Gemini API なら、入力を Google の人が読む可能性があると規約にある【公式】（URL は 2節の表）。同意文に書くか、有料のキーにするかを決める必要がある
5. 今のフロントは React 19 + Vite 8 で、初回の JS は gzip 後 76 KB【実測】。軽さの面では作り直しの技術を変える必要は薄い

## 1. 解決したい問題

大学に入ったばかりの1年生は、学習履歴が無く、やりたいことを言葉にしにくい（Yuto 2026-10-31 のコールドスタートの話【vault】）。その学生が、ガイダンス期間に自分のスマホで履修の相談をし、根拠（どの科目のシラバスか）を見ながら納得して科目を選べることを、関西大学の学生へのインタビューとアンケートで確かめたい（HCI 評価。10/21・10/28 MTG で合意【vault】）。

今のフロントは React のテンプレートに入力欄と出力欄のあるタブを足しただけの疎通テスト用で（10/28 MTG【vault】、`frontend/src/App.tsx`【リポ】）、協力者の端末で使ってもらう前提になっていない。作り直さないと、インタビューの最中に「止まって見える」「記録が残らない」「警告が出て開けない」が起きる。

## 5. ペルソナ別の要件

### P1 入学直後の1年生（スマホ中心。ガイダンス期間に移動中に使う。学内 Wi-Fi やモバイル回線）

困ること:
- 送ってから 1〜1.5 分、何も変わらないと壊れたと思って閉じる（待ち時間は 2節）
- 地下鉄やエレベーターで回線が切れる。アプリを切り替えるとブラウザが通信を止めることがある【推定】。1分待った回答が消えると、もう一度は送らない
- 何を聞けばよいか分からない。聞いても、科目コードや専門用語が並ぶと読めない
- 回答が正しいか判断できない。どのシラバスに書いてあるのかを見たい
- 証明書の警告が出たら開かない
- 登録やログインを求められたら閉じる
- 日本語の変換を確定する Enter で、書きかけの質問が送られてしまう（チャット欄でよく起きる不具合）【推定】

| ID | 要件 | 種別 | 優先度 | 受け入れ基準 |
|---|---|---|---|---|
| R1-1 | 送信したらすぐ待機状態を出し、経過時間を見せる。ストリーミングがあれば段階（探索中・出典の確認中など）も出す | 機能 | 必須 | 送信から 1 秒以内に待機表示。経過秒が 1 秒以上の間隔で更新される。30 秒を超えたら「時間がかかっています」の旨を出す（文言は UX 側） |
| R1-2 | 待ち時間に上限を設け、超えたら理由と再試行の手段を出す。エラーを握りつぶさない | 機能 | 必須 | クライアント側の上限は 180 秒を提案（観測の最大 101 秒の約 1.8 倍。【推定】）。上限・ネットワーク断・HTTP 4xx/5xx のそれぞれで、別の表示になる |
| R1-3 | 送った質問と受け取った回答を、ページを再読み込みしても消えないように端末内に一時保存する | 機能 | 必須 | 回答表示後に再読み込みしても同じ回答が見える。保存先は `sessionStorage`（タブを閉じたら消える。P2-6 と両立） |
| R1-4 | 回線が切れても回答を取り戻せる（ジョブ ID で後から取りに行く、など） | 機能 | 後 | バックエンドに非同期ジョブの API が要る（`questions-for-yuto.md` Q4・Q10） |
| R1-5 | 出典を回答と一緒に出す。`sources[]` の科目名・コード・担当・曜日時限・単位・抜粋を表示できる。`unverified_codes` は「DB で確認できなかった」と区別して出す | 機能 | 必須 | API の 1 レスポンスの `sources` が全件表示できる。`unverified_codes` が空でないときに、色以外（文字）でも区別できる |
| R1-6 | API の応答の種類を区別して扱う: MCP の回答 / 静的経路の回答（`route="static"` と `notes`）/ 聞き返し（質問があいまいで候補を返す）/ エラー | 機能 | 必須 | 4 種類それぞれのレスポンス例（手で作った JSON）で表示が崩れない |
| R1-7 | LLM の回答文を HTML として埋め込まない。Markdown を表示するなら、生の HTML を通さない描画にする | 非機能（安全） | 必須 | `dangerouslySetInnerHTML` を使っていない。回答に `<script>` を含めたテスト用 JSON で、スクリプトが動かない |
| R1-8 | 幅 320〜430 CSS px のスマホで、横スクロールせずに全部読める | 非機能 | 必須 | 320 px 幅で横スクロールが出ない（WCAG 2.2 の 1.4.10）。iOS Safari と Android Chrome の実機で1回ずつ確認 |
| R1-9 | 初回表示を軽く保つ（JS の予算） | 非機能 | 必須 | G4。依存を足すときは `npm run build` の後に gzip 後の大きさを見る |
| R1-10 | 正規の証明書の HTTPS で配信する | 非機能 | 必須 | 協力者の端末のブラウザで警告が出ない。担当はサーバー側（`questions-for-yuto.md` Q1） |
| R1-11 | ログインなしで使える | 機能 | 必須 | URL を開くだけで質問できる |
| R1-12 | 日本語入力の変換中の Enter で送信しない | 機能 | 必須 | `KeyboardEvent.isComposing` が true の Enter を無視する。iOS と Android の日本語キーボードで確認 |
| R1-13 | 何を聞けばよいか分からない人向けの入力補助（例文など）を、コードに埋め込まずデータとして持てる | 機能 | 必須（UX 側が例文を出すと決めたら） | 例文を 1 ファイル（JSON など）の差し替えで変えられる。中身と見せ方は UX 側 |
| R1-14 | 前の回答を踏まえた追質問（マルチターン） | 機能 | 後 | バックエンドの対応が先（実験6） |
| R1-15 | オフラインで開ける・ホーム画面に置ける（PWA） | 非機能 | 後 | — |

### P2 インタビューを実施する Aki_Ha（対面またはオンラインで短時間。協力者の端末で開いてもらう。何が起きたかを記録したい）

困ること:
- 協力者の端末（iOS・Android・PC がばらばら）で、その場で確実に開けないと時間を失う。今は公開先が開けない（2節）
- 1 問に 1〜1.5 分かかるので、15 分のインタビューなら質問は数問しかできない【推定】。インタビューの組み立てに直結する
- 何を聞いて、何が返って、何秒かかって、どこで失敗したかを後から見たい。今の MCP 経路はログを残さない
- 協力者の端末に会話の履歴を残したくない
- その場で API が落ちたとき、画面から原因が分からないと立て直せない

| ID | 要件 | 種別 | 優先度 | 受け入れ基準 |
|---|---|---|---|---|
| R2-1 | 参加者 ID（仮名。例 `K01`）を開始時に決め、以後の全リクエストに付ける。氏名や学籍番号は使わない | 機能 | 必須 | 参加者 ID をインタビュー用の URL か開始画面で渡せる。全リクエストに付いている（ログで確認） |
| R2-2 | 1 リクエストにつき 1 行の記録を残す: 時刻 / 参加者 ID / 条件 ID / 質問文 / レスポンス全体（`route`・`answer`・`sources`・`unverified_codes`・`notes`・`tool_calls`・`model`・`latency_ms`）/ クライアント側の待ち時間 / エラーの内容 / フロントのコミット | 機能 | 必須 | ログの行数が送信回数と一致する。記録先はサーバー（協力者の端末ではない）。バックエンドの変更が要る（`questions-for-yuto.md` Q5） |
| R2-3 | URL 1 つで開ける。QR コードで渡せる長さにする | 機能 | 必須 | インストール・ログイン不要。URL に個人を特定する情報を入れない |
| R2-4 | 失敗を画面に出す: タイムアウト / ネットワーク断 / サーバーのエラー（503 は Neo4j に繋がらない等）/ 静的経路への切り替え（`notes` の理由） | 機能 | 必須 | 共通の例外ハンドラが返す 409・502・503（【リポ】`backend/src/course_core/errors.py`）と、FastAPI の 422・500 を、手で作った応答で表示できる |
| R2-5 | インタビュー前日に、本番の URL・実機で通しの確認ができる | 非機能 | 必須 | チェックリスト（iOS・Android・PC で開く、1 問送って回答と出典が出る、ログに 1 行増える）を前日に通す |
| R2-6 | 協力者の端末に会話を残さない | 非機能 | 必須 | `localStorage`・IndexedDB を使わない。`sessionStorage` だけにして、終了時にタブを閉じれば消える |
| R2-7 | インタビュー中に、Aki_Ha の端末から今のやり取りを見られる（オンライン実施の画面共有の代わり） | 機能 | 後 | — |
| R2-8 | ログを CSV で取り出す管理用の画面 | 機能 | 後 | インタビューまでは JSONL をサーバーから取り出せば足りる |

### P3 バックエンド担当の Yuto（締め切り直前で、バックエンドの変更をなるべく増やしたくない。Python）

困ること:
- フロントの作り直しのために API の形を変えると、論文の作業時間が減る
- フロントの言語が増えると、レビューができない
- 自分の Pydantic の型を変えたとき、フロントがどこで壊れるかが見えない
- 公開先のサーバー（GMS）の面倒を見ているのは自分【推定】で、そこに手を入れる作業が増える

| ID | 要件 | 種別 | 優先度 | 受け入れ基準 |
|---|---|---|---|---|
| R3-1 | インタビュー版は今の `POST /api/test/agent/mcp` と `McpAgentRunResult` をそのまま使う。バックエンドに頼む変更は、ログ（R2-2）と、必要なら進捗のストリーミング（R1-1）に絞る | 非機能 | 必須 | 頼む変更が `questions-for-yuto.md` の Q5・Q10 に挙げたものだけ |
| R3-2 | フロントの型は `McpAgentRunResult` を写した TypeScript の `interface` を 1 か所に置く（今の `McpAgentTest.tsx` の定義を移す） | 非機能 | 必須 | 型の定義が 1 ファイル。`any` を使わない（`frontend.md` のルール【リポ】） |
| R3-3 | FastAPI の `/openapi.json` から TypeScript の型を作る | 非機能 | 後 | Pydantic を変えたら、生成した型の差分で壊れる場所が分かる |
| R3-4 | フロントは静的ファイル（HTML・JS・CSS）だけにし、Node のサーバーを常時動かさない | 非機能 | 必須 | ADR-0004 の判断（SSR 不要・Node サーバーの二重運用を避ける）と同じ【リポ】 |
| R3-5 | 本番では Vite の開発サーバーでなく、ビルドした成果物を配る | 非機能 | 必須（GMS に置くなら） | `frontend/Dockerfile` を2段階（ビルド → 静的配信）にする。開発用の設定とは分ける。サーバーの compose の変更なので Yuto の了承が要る（`questions-for-yuto.md` Q3・Q9） |
| R3-6 | 同じオリジン（`/api`）で API を呼ぶ構成なら、CORS の設定を足さない | 非機能 | 必須（GMS に置くなら） | 別のオリジンに置くなら、`CORSMiddleware` で許可するオリジンを 1 つに絞る（ワイルドカードにしない） |

### P4 実験と評価の担当の Ibuki（アンケートとの紐づけ、条件の管理、倫理・同意）

困ること:
- アンケート（Google フォーム等【推定】）の回答と、システムの操作ログを同じ人として突き合わせたい
- 条件（たとえば MCP と静的、出典の有無、10/13 に話が出た「条件を伏せて2つの回答を比べる画面」）を参加者に見せずに切り替え、取り違えずに記録したい。今は経路が環境変数で決まり、リクエストごとに切り替えられない【リポ】`runner.py`
- 同意を取らずにデータを集めると、論文に使えない。無料枠の Gemini なら、入力を Google の人が読む可能性がある（2節）
- 関西大学の学生のデータが、駒澤大学のサーバーと Google に送られる
- 後から「どのモデル・どのプロンプト・どのコミットの結果か」が分からないと、論文に書けない

### P6 アクセシビリティが必要な学生（スクリーンリーダー、色覚、拡大表示）

困ること:
- 回答が届いたことにスクリーンリーダーが気づかない。逆に、ストリーミングで 1 文字ずつ読み上げられると聞けない
- 「確認できなかった科目」などが色だけで示されると分からない
- 200% に拡大すると横にはみ出す、ボタンが小さくて押せない
- ページの言語が英語（`lang="en"`）になっていて、日本語が英語の音声で読まれる【リポ】`index.html`

基準は WCAG 2.2（W3C 勧告 2024-12-12。https://www.w3.org/TR/WCAG22/ 【公式】）の A と AA。

| ID | 要件 | 種別 | 優先度 | 受け入れ基準 |
|---|---|---|---|---|
| R6-1 | `<html lang="ja">` にし、ページのタイトルを付ける | 非機能 | 必須 | `index.html` で確認 |
| R6-2 | 回答の到着と待機の状態を、フォーカスを動かさずに読み上げさせる（4.1.3 状態メッセージ）。ストリーミングの途中は読み上げさせず、届き終わったら 1 回だけ知らせる | 非機能 | 必須 | `aria-live="polite"` などの領域がある。VoiceOver か TalkBack で、回答の到着が 1 回だけ読まれる |
| R6-3 | 色だけで意味を伝えない（1.4.1）。文字のコントラスト 4.5:1 以上（1.4.3）、部品の境界 3:1 以上（1.4.11） | 非機能 | 必須 | axe の自動チェックで違反なし |
| R6-4 | 200% に拡大しても内容が欠けない（1.4.4）。320 CSS px で横スクロールが出ない（1.4.10） | 非機能 | 必須 | ブラウザの拡大 200% と、幅 320 px で確認 |
| R6-5 | キーボードだけで操作でき、フォーカスが見える（2.4.7） | 非機能 | 必須 | Tab で送信まで行ける。フォーカスの枠が見える |
| R6-6 | 押す部品は 24×24 CSS px 以上（2.5.8） | 非機能 | 必須 | 開発者ツールで寸法を確認 |
| R6-7 | 動きを減らす設定（`prefers-reduced-motion`）を尊重する | 非機能 | 必須 | 待機表示のアニメーションが、設定で止まる |
| R6-8 | 時間制限で入力を消さない（2.2.1）。R1-2 のタイムアウトの後も、質問文は残して再送できる | 非機能 | 必須 | タイムアウト後に入力欄に質問文が残っている |
| R6-9 | アクセシビリティの自動チェックを CI に入れる | 非機能 | 後 | — |
