1. **開いた時点で、最初の提案がもう出ている（操作0回）。** 学科の履修系統図から機械的に選んだ「まず見ておきたい科目」3件（系統図で多くの方向につながる枠の科目）を、理由つきで出す〔C23〕。好みはまだ聞かない。

### 1.3 「楽な授業」「友達と同じ授業」に流れる理由

|---|---|---|
| 能力 | シラバスの専門用語が読めない。科目どうしのつながりを知らない。だから内容で比べられない | 言葉で答えさせず、選択肢から選ばせる。科目ごとに短い理由と、授業計画の具体的な回を見せる |
| 機会 | 情報は公開されているが、科目ごとにばらばら（点）。比べる道具がない。すぐ手に入るのは友達と先輩の話だけ | 系統図の線（点と点のつながり）を、開いた瞬間に見せる |
| 動機 | 中身が分からないなら、失敗を避けるのが合理的になる（損失回避）。友達と同じなら失敗しても1人ではない | 「楽さ」に代わる安心材料を出す。「多くの方向につながっている」〔C23〕「後で選べる科目が減らない」。人気（みんなが取っている）は出さない。同調を強めるだけで、この製品が変えたい行動そのものだから |

### 1.4 時期のずれ

調査は11月。1年生の協力者も入学から7か月たっている。S1 の「入学直後」を再現するには、(a)「入学直後の4月に戻ったつもりで」と教示するか、(b)「次の学期以降（2年）の科目」を探してもらうか、のどちらかが要る。画面はどちらにも対応できる（メニューの「想定の時点」にどの時点を想定しているかを出し〔V2-05〕、リンクで指定できるようにする。6.2 の W1）。どちらにするかは研究計画の判断なので、10章で確認する。

## 3. コールドスタートの核となる体験

### 3.1 結論

「言葉にしてもらってから提案する」のをやめる。**先に提案を見せ、反応で好みを形にしてもらう。**

1. 開いた時点で、系統図から機械的に選んだ「まず見ておきたい科目」3件が理由つきで見えている（0操作）〔C23〕。
2. 方向を1タップで選ぶと、その方向へ至る科目が取る順に並ぶ（1操作）。
3. 理由を見る・候補に入れる・つながる先の枠をたどる、という反応を重ねるうちに、自分の関心が形になる。
4. 言葉にできる人だけが、自分の言葉で探す（任意）。

### 3.2 4つの原則と根拠

**原則1 構造を先に、好みは後に（意味のある既定値）**

- 1年生には好みのデータが無い（学習履歴が無く、言葉にもしにくい）。そもそも好みは、尋ねられたその場で作られることが多い [2]。白紙の入力欄は、その「その場で作る」作業を学生に丸ごと渡してしまう。
- 好みが分からなくても言えることが1つある。**「多くの方向につながる枠の科目を取っておけば、後で選べる道が減りにくい」**。これは系統図だけで決まり、LLM も好みも要らない。これを既定の提案にする。
- 既定値は選ばれやすい。メタ分析では効果量 d = 0.68 で、研究ごとのばらつきも大きい [3]。効果が強いので、次の4条件を守る。
  1. 既定の理由を画面に書く。v2 では、行ごとのなぜ（印＋灰の文字。例「3分野につながる（系統図）」）と、「ほかに N 科目」を開いた中の並びの説明の1文で言う。v1 の「好みはまだ使っていません」は出さない〔V2-06〕。
  2. 候補に自動で入れない。候補は空から始まる。ただし学科の必修は「候補」でなく決まった科目として、時間割に最初から灰で入れておく（区分のデータがあるとき。無いあいだは入れない。6.3）〔V2-09・V2-15〕。
  3. 1タップで別の方向に変えられる。
  4. 学生の利益（後の選択肢を残す）に沿う。

**原則2 思い出させずに、見て選ばせる（再認）**

- 「やりたいこと」を思い出して書く（再生）より、並んだものから選ぶ（再認）方が負担が小さい [4]。
- 方向は専門分野名でなく日常の言葉で書く。例: 「応用化学工学系」でなく「環境とプロセス: 工場の装置や、水・空気をきれいにする仕組みを設計する」。1年生は科目名の語彙をまだ持っていない（作り手が自分の知識を前提にしてしまう「知識の呪い」の回避）。
- 詳細では、抽象的な概要より授業計画の具体的な回（「第5回 水質の指標」など）を先に見せる。

**原則3 小さく見せる**

- 選択肢が多すぎて決められなくなる現象は、いつも起きるわけではない。メタ分析 [5] では、好みがはっきりしないとき（preference uncertainty が高いとき）と、選択肢が複雑なときに起きやすい。1年生はこの両方に当てはまる。
- 提案は1度に3件まで。残りは「ほかに N 件」で開ける（隠したことは件数で必ず書く）。方向は5個（既定を含む）。カードの文は「なぜ」1行まで。詳しい根拠は1タップ先に置く（段階的開示 [6]）。
- 選択肢を減らし、並べ方を整え、既定値を置くのは、選択アーキテクチャの基本の道具である [7]。

**原則4 理由とセットで、いつでも戻れる**

- 提案には必ず「なぜ」と根拠の種類を付ける（7章）。
- 候補に入れても外せる。一覧の＋（詳細では［候補に入れる］）は押すとその場で入った状態（緑の輪とチェック。詳細では「候補に入っています」）に変わり、もう一度押すと外れる〔C04〕。入れたときは、時間割のどこに入ったかを小さな時間割で見せる知らせを一瞬出す（6.2 の W4-add）。入れたことの取り消しは同じ＋をもう一度押す〔V2-16〕。時間割の［外す］のあとは「◯◯を外しました ［元に戻す］」を5秒出す。［元に戻す］にフォーカスかマウスがあるあいだは消さない〔V2-31〕。候補は履修登録ではないと画面に書く。取り返しがつくと分かっていれば、失敗を恐れる選び方は弱まる（後悔回避への手当て）。

### 3.3 最初の価値

最初の価値 =「知らなかった科目を1つ、取る理由と、その先にどの枠が続くかとセットで知ること」。

- 操作0回で得られる（まず見ておきたい科目〔C23〕）。
- 方向を選べば、自分に寄せた最初の価値に1操作で届く。

### 3.4 体験の段階

| 段 | 学生がすること | 画面 | 操作数 | 使うデータ | 待ち |
|---|---|---|---|---|---|
| 0 | 開く | W1 さがす（既定） | 0 | 同梱の学科データ（系統図とシラバス） | なし |
| 1 | 方向を1つ選ぶ | W2 さがす（方向） | 1 | 同上 | なし |
| 2 | 理由を見る・候補に入れる・枠をたどる | W3 詳細、W4 候補 | 1回ずつ | 同上 | なし |
| 3 | 言葉で探す（任意） | W5 自分の言葉で探す | 3 | 既存の AI エンドポイント | 30秒〜1分半〔T3〕 |

段0〜2は LLM を通さないので待たない。段3だけが待つ。

### 3.5 使わない手法

| 手法 | 使わない理由 |
|---|---|
| 入口に白紙の入力欄（チャット画面から始める） | 言葉にできない人がそこで止まる。S1 の前提に反する |
| 長い興味診断（10問を超える質問票） | 始めるまでの負担が大きい。答えがその場で作られて不安定（原則1）。質問と科目を結ぶ仕組みが新たに要り、K2 が増える |
| 人気・履修者数・「みんなが選んだ」 | 同調を強める。この製品が変えたい行動そのもの。データも無い |
| 締め切りの煽り、「取らないと損」 | 不安で選ばせることになる。操作的な誘導（ダークパターン）の類型 [8] に当たる |
| 候補への自動追加、チェック済みの初期値 | 自分で選んだ感覚がなくなり、研究で測る「納得」もゆがむ |
| 「AI が最適な科目を選びました」 | 過信を招く。根拠の強さに見合った信頼にとどめる [9] |
| 点数・順位・星 | 「よい順」に見える。並びの理由（取る順、つながる方向の数）だけを書く |

### 3.6 既定値の副作用と、その手当て

既定の3件は、同じ学科の全員に同じものが出る。全員が同じ科目に寄れば、「友達と同じ授業」を別の形で作ってしまう恐れがある。

- v1 は見出しに「この学科の誰にでも同じものを出しています」と書いていた。v2 では W1 に見出しを置かないので、この文も出さない。並びの決め方は「ほかに N 科目」を開いた中の1文で言う〔V2-05〕。
- 方向の選択肢を既定の提案のすぐ上に置き、1タップで自分の方向に変えられるようにする。
- 指標「既定依存率」（11章）を見る。高すぎれば、既定を2件に減らす、方向を先に見せる、などを検討する。

なお、この学科の1年次の枠の科目は必修が多い可能性がある（前提。区分のデータは確認事項）。v1 は必修でも既定の提案に出し、「この必修科目は3年の3つの方向につながっている」と知ることに意味がある、とした。v2 では、区分が分かれば必修を一覧から外して時間割に入れておき、W1 の状況の1行で「1年春の必修 N科目は、時間割に入れてあります」と言う。一覧は選択と他学部の科目だけにする。必修のつながる先は、時間割のマスから開く W3 の取る順で見られる〔V2-09〕。区分が分からないあいだは、一覧から必修を外せないので v1 と同じく必修も出し、W3 の区分は「準備中」と書く。v1 の一覧の下の「必修・選択の区分はまだ出せません」の行〔C16〕は出さない（6.3）〔V2-12〕。

### 3.7 おすすめ（v1 の「まず見ておきたい科目」）の選び方（フロントで計算）〔C23・V2-17〕

- **入力:** 同梱の学科データ（枠・線・科目）。
- **手順:**
  1. 想定時点（既定は1年の入学直後）の学年の枠を集める。
  2. 枠ごとに、`prerequisite` 型の線を下流へたどり、届く「方向」の数を数える（方向は 3.8 の表の4つ。3年次の4枠と4年次の法規・知財の枠を4つの方向にまとめたもので、そのどれか1つの枠に届けば、その方向に届いたと数える）。
  3. 多い順に並べる。同数なら学科の枠を全学共通の枠より先にし、次に届く枠の総数が多い順、最後に系統図の記載順。
  4. 上位3枠から1科目ずつ出す（同じ枠から3件並ぶのを避ける）。枠の中は学期（春が先）→系統図の記載順で選ぶ。同じ枠のほかの科目は、カードに「同じ枠にほかに N 科目」と書く。
- **理由の文（機械的に作る）:** 「この科目の枠から、3年の4つの方向のうち3つへ系統図の線がつながっています」。
- **今のデータでの例（取り込み中のデータのテストに書かれた線から数えた。確定ではない）:** 無機・基礎化学系の枠は、物理化学系・分析・有機化学系を経て、応用化学工学系・材料・エネルギー系・有機・触媒系の3方向に届く。化学工学・エネルギー・基礎数理系の枠は2方向に届く。
- **縮退:** 想定時点の学年に枠が無ければ（3年以降など）、既定の提案の代わりに方向の選択を先頭に出す。
- **v2 での変更〔V2-17・V2-09〕:**
  - 一覧に必修を出さない（区分のデータがあるとき）。手順4で科目を選ぶとき、必修を飛ばす。必修は時間割に入れておく。
  - 一覧に出すのは3件と「ほかに N 科目」（開くと残りの科目と並びの説明。E1 の見本は残り2件）。3件のうち2件は手順1〜4で選び、1件は卒業に足りない区分（例: 教養）から、時間割の空いた曜限に入る教養や他学部の科目を選ぶ。卒業要件で選んだ科目の理由は「教養があと4単位（卒業要件）」の形。卒業要件のデータが入るまでは、3件とも手順1〜4で選ぶ（6.3、U3）。
  - 実装で決まった計算〔V2-32〕: 想定の学期の必修でない科目を、3年の分野へつながる数が多い順（同じなら系統図の記載順）に並べ、先頭の2つを出す。卒業要件があり教養が足りなければ、残りから必修と重ならない教養の科目を1つ選ぶ（他学部の科目を先に選ぶ）。足りているか卒業要件が無ければ、3件ともつながる数の順。残りは「ほかに N 科目」。「時間割の空いた曜限に入る」は、必修と重ならないこととした（候補とは比べない）。
  - 理由の文を短くする。一覧の行は「3分野につながる（系統図）」、詳細は「3年の4分野のうち、3つへ線がつながる科目です」と「履修系統図より」（7.2）。カードの「同じ枠にほかに N 科目」は出さず、W3 の取る順の中の「同じまとまりの科目」で見る。
  - 並びの説明は「ほかに N 科目」を開いた中の1文「3年の多くの分野につながる順に2つと、卒業に足りない区分から1つを出しています。」（卒業要件が入るまでは、後半を除いた文にする）。

### 3.8 興味関心（v1 の「方向」）の作り方〔V2-04〕

- **数:** 既定を含めて5個（7個以内に収める）。
- **元にするもの:** 系統図の3年次の枠と4年次の法規・知財の枠。学科自身の分け方なので、研究者の想像で方向を作るより偏りが小さく、根拠も「系統図」と書ける。
- **言葉:** 日常の言葉で10字程度のラベルと、選んだあとに出す1行の説明。下は**仮の案**。学科の学生（Yuto など）が科目データを見て決め直す。

| チップのラベル（仮） | 選んだあとの説明（仮） | 対応する枠 |
|---|---|---|
| おすすめ（既定）〔C23・V2-01〕 | 系統図で多くの分野につながるまとまりの科目と、卒業に足りない区分の科目 | 計算で決まる（3.7） |
| 環境とプロセス | 工場の装置や、水・空気をきれいにする仕組みを設計する | 応用化学工学系（3年） |
| 材料とエネルギー | 電池や新しい素材の性質を調べてつくる | 材料・エネルギー系（3年） |
| 有機と触媒 | 分子をつくる反応と、反応を速める触媒 | 有機・触媒系（3年） |
| 技術と社会 | 安全・倫理・法律・品質など、技術を仕事で使うときのこと | 安全・倫理・特別講義系（3年）、法規・知財・マネジメント（4年） |

- **方向を選んだときの提案:** その方向の枠へ、線を逆にたどって至る枠の科目を、1年→2年→3年の段に分けて並べる。段の見出しに「この枠から次の段の◯◯へ線がつながる」と書く（これがその段の科目の「なぜ」になる）。
  - 段の中は枠ごとの小見出し（枠の名前）に分け、枠ごとに[この枠の科目をすべて見る（N 科目）]を置いて W13 へ進めるようにする〔C02〕。
  - 各段で見せる科目は3件まで。段の中の枠から、学期→系統図の記載順の先頭を1件ずつ順に取り、3件になるまで繰り返す（枠が1つなら、その枠から3件）。枠が4つ以上ある段では、4つ目からの枠は小見出しと[この枠の科目をすべて見る]だけを出す。
  - 枠の中の並びは関係の強さの順ではないこと、同じ枠の科目は系統図の上では同じ関係であることを画面に書く〔C24〕。
- **v2 での変更〔V2-22〕:** 段は学年の見出し（「1年」「2年」「3年」の1語）だけにする。段の見出しの「なぜ」、枠ごとの小見出し、[この枠の科目をすべて見る（N 科目）]〔C02〕、並びの注記〔C24〕は置かず、行ごとのなぜ（例「3年の『環境とプロセス』につながる（系統図）」）と、一覧の最後の1文「取る順に、1年から並べています（履修系統図）」で言う（E1 の見本の W2）。各段で見せる科目の数と選び方（学期→系統図の記載順で3件まで）は v1 のまま。
- チップの並びは E1 の見本の順（おすすめ、環境とプロセス、有機と触媒、材料とエネルギー、技術と社会）。375px で2行に収まる（`docs/frontend/DESIGN.md` 4章）〔V2-04〕。

## 4. シナリオ別のフロー

## 5. 情報設計とナビゲーション

### 5.1 情報の構造

```
学科（リンクで決まる。メニューから変更。調査モードでは固定）
├─ さがす
│   ├─ 興味関心: おすすめ（既定） / 興味関心4つ
│   │    └─ 提案（3件＋ほかに N 件。興味関心では 1年→2年→3年 の段）
│   │         └─ 科目の詳細（授業でやること・なぜ・開閉〈取る順・授業計画・
│   │            成績のつけ方と教科書〉・原文）
│   │              └─ 取る順の科目の詳細（同じ型の画面）
│   └─ 探す（一覧のいちばん上の欄。例文「例：環境に関わる仕事がしたい」。文で書くと AI へ）
├─ 時間割（その学期の必修と候補。曜日×時限の表）
└─ メニュー: このAIについて / 学科を変える / 想定の時点 / 時間割を文字でコピー
調査モードのときだけ: 調査の開始 → … → 使い終わった（記録とアンケート）
```

- v2 で変えた〔V2-02・V2-04・V2-11・V2-18・V2-19〕: 上位の行き先「候補」を「時間割」にした。「このAIについて」と学科の変更はメニューに入れた。自由記述の入口は「さがす」の中の上の帯の探すにした（実装のあと、さがすの一覧のいちばん上の欄に移した〔V2-36〕）。詳細の中身は授業でやることとなぜを先に出し、ほかは開閉に畳む。

### 5.2 スマホ（幅 840px 未満。375px を基準に設計）

**決めたこと**

- 上位の行き先は「さがす」「時間割」の2つ。画面の下に、線のアイコンと文字のラベルつきで常に見えるタブを置く。「時間割」にはこの学期の単位を出す（例「時間割 5単位」。必修を含む）〔V2-19〕。
- 上の帯: サービス名とメニューの印〔V2-02・V2-36〕。v2 で置いた探すの印はやめた（自分の言葉で探す欄は、さがすの一覧のいちばん上に出す）〔V2-36〕。調査モードでは帯の上に［使い終わった］の帯を出す（8.1）。
- メニュー（ハンバーガー）には二次的な行き先だけを入れる: このAIについて、学科を変える（今の学科名を添える。調査モードでは変えられない）、想定の時点（1年の入学直後）、時間割を文字でコピー。どれも1回の利用で1度使うかどうかのもの。主な行き先の「さがす」「時間割」はメニューに入れない。調査モードの［使い終わった］も、参加者が必ず押すものなのでメニューに入れない〔V2-02〕。
- 科目の詳細は別の画面（URL を持つ）に進む。下からせり上がるシートにはしない。詳細は長く、戻る操作をブラウザの「戻る」と一致させたいから。詳細の上の帯の戻るは、来た一覧の名前（「＜ 環境とプロセス」）にする。パンくずはスマホでは使わない（375px で3段以上のパンくずは折り返して2行になり、上の帯に収まらない）〔V2-20〕。
- 「自分の言葉で探す」は「さがす」の中の1つの入口にする。さがすの一覧のいちばん上（興味関心のチップの上）に欄を常に出し、欄の中は左に探すの印、例文は「例：環境に関わる仕事がしたい」〔V2-36〕。チャットを独立したタブにしない。v1 の W1 の［自分の言葉で探す］のボタン〔V2-18〕と、v2 の上の帯の探すの印〔V2-36〕はやめた。
- 欄にカーソルが入ると、欄のすぐ下に外部の AI に送る注意と［探す］を出す（W5-1）。欄にカーソルがあるか、送っていない文が入っているあいだは、興味関心のチップを隠す（状況の1行と提案の一覧は残す）。空のままカーソルが外れたらチップを戻す。送ったら注意と［探す］を畳んでチップを戻す（送った文は欄に残る〔C11〕）。チップを戻すときは開閉の中身と同じフェードで、隠すときは動かさない。動きを減らす設定ではどちらも動かさない〔V2-36〕。
- 自由記述の回答を待っているあいだは、どの画面でも下部ナビのすぐ上に1行の状態（「回答を作っています 0:24 [やめる]」）を出し、届いたら「回答が届きました [見る]」に変える。[見る]で W5-3 へ進む〔C08〕。

**根拠**

| 判断 | 根拠 |
|---|---|
| 二次的な行き先だけをメニュー（ハンバーガー）に入れる〔V2-02〕 | v1 は「隠したナビは、見えているナビより見つけられにくく、課題にかかる時間も長くなり、難しく感じられる（NN/g の定量調査）」を根拠にハンバーガーを使わないとした（https://www.nngroup.com/articles/hamburger-menus/ ）。v2 でも主な行き先（さがす・時間割）は隠さない。メニューに入れるのは1回の利用で1度使うかどうかの行き先だけで、毎回の画面から外すと W1 の文字と押せる物が減る（指示 F1・F5。オーナーが v1 の決定を上書きした。E1 の `redesign.md` 6章） |
| 下部ナビにする | スマホは片手・親指で操作されることが多く、画面の下側が届きやすい（Hoober の観察）。https://www.uxmatters.com/mt/archives/2013/02/how-do-users-really-hold-mobile-devices.php |
| 行き先は2つ | Material 3 のナビゲーションバーは3〜5個の行き先を想定している（Compose の NavigationBar の説明）。https://kotlinlang.org/api/compose-multiplatform/material3/androidx.compose.material3/-navigation-bar.html 。本案はその範囲より少ない。Material 3 を元にした SAP Fiori for Android の指針は2〜5個を認めている。https://www.sap.com/design-system/fiori-design-android/v26-1/components/m3-standard-components/navigation-bar/usage 。数合わせのために、使う頻度の低い画面（このAIについて）をナビに入れることはしない。2つの下部ナビが不自然に見える場合の代わりは「見出しの下に固定した2つのタブ」。ただし親指から遠いので第一案にはしない |
| 「候補に入れる」はナビに置かない | タブバーは移動のためのもので、操作（アクション）のためのものではない（Apple Human Interface Guidelines, Tab bars）。https://developer.apple.com/design/human-interface-guidelines/tab-bars |
| チャットを独立タブにしない | 独立させると、白紙の入力欄が1つの行き先として目立ち、言葉にできない人の行き止まりになる（3.5） |

### 5.4 URL と「戻る」

- 画面ごとに URL を持つ（`/`、`/?dir=<方向>`、`/course/<科目コード>`、`/group/<枠ID>`、`/shortlist`、`/about`、`/ask/<端末内の番号>`〔C06〕）。ブラウザの戻る、Android の戻るジェスチャで1つ前に戻れる。

### 5.5 状態の保存

- 候補は端末のブラウザに保存する（アカウントは作らない）。時間割の画面に「候補は履修登録ではありません。この端末のブラウザにだけ保存されます。」と書く。別の端末に移すには、メニューの「時間割を文字でコピー」を使う〔V2-02〕。
- 自由記述の質問と回答は、タブを開いているあいだ保持する（W3 へ進んで戻っても結果が残る）。タブを閉じると消える〔C06〕。
- 調査モードでは、[始める]で前の状態を消す。消すものが残っているときは、件数を出して確かめる〔C18〕。

### 5.6 文言の方針

- できないことは短く書き、代わりにできることと一緒に出す。
- 感嘆符・絵文字・記号の飾りは使わない。

## 7. 提案の理由と根拠の見せ方（信頼と納得）

### 7.1 3段の見せ方

1. **提案の科目（0操作で見える）:** 曜限・単位・科目名・授業でやることと、「なぜ」の1行（印と灰の文字。根拠の名前をかっこで添える）〔V2-03・V2-10〕。
2. **詳細（1操作）:** 5つの項目（曜限・単位・対象・区分・担当）、授業でやること、なぜ。取る順（前後と同じまとまりの科目）・授業計画・成績のつけ方と教科書は開閉に畳み、開いたときだけ見る。最後に使っていない情報の1文〔V2-11〕。
3. **原文（2操作）:** 大学のシラバスのページ（取り込み済みデータの `detail_url`）。

### 7.2 根拠の種類を分けて書く

| 画面の表記（v2〔V2-03〕） | 中身 | 作り方 | 確かさ |
|---|---|---|---|
| 一覧「（系統図）」、詳細「履修系統図より」 | まとまりどうしの線、分野の数 | 学科データから機械的に計算（LLM なし） | 系統図の通り。ただし PDF の自動読み取りなので、読み取りの誤りはありうる |
| 詳細「2026年度シラバスより」 | 授業でやること（概要）・授業計画 | シラバスの文をそのまま引用 | 原文の通り（年度を明記） |
| 一覧「（卒業要件）」 | 卒業に足りない区分（3.7） | 学科の卒業要件と時間割から計算（LLM なし） | 卒業要件のデータが入ってから出す（6.3、U3） |
| 一覧・詳細「（AIの判断）」、詳細「間違うことがあります」の1文 | 自由記述と科目が合う、という判断 | LLM の回答 | 間違うことがある、と毎回書く |
| 根拠: 内容の近さ | 類似度の線（`SIMILAR_TO`） | origin/main に無い。ADR-0016 で次フェーズ〔T5〕 | 線ができたら出す。今は出さない |

- **v2 では根拠の種類を色・形で目立たせず、灰の文字だけで書く**（指示 F8。オーナーが v1 の「根拠の種類を色・形・文字で毎回目立たせる」を上書きした。見た目は `docs/frontend/DESIGN.md` 3.2）〔V2-03〕。v1 の「根拠: 履修系統図」「シラバスより」「根拠: AIがシラバスから判断」のラベルは使わない。
- **どこから来た提案かで「なぜ」が変わる。**
  - 既定（おすすめ）: 一覧「3分野につながる」、詳細「3年の4分野のうち、3つへ線がつながる科目です」。卒業要件で選んだ科目は「教養があと4単位」〔V2-17〕
  - 興味関心: 一覧「3年の『環境とプロセス』につながる」「『環境とプロセス』の科目」、詳細「選んだ『環境とプロセス』の3年の科目です」〔V2-17〕
  - 前後の枠をたどった先: 「◯◯（元の科目）の枠から線がつながる枠の科目です」
  - 自由記述: AI の説明のその科目の段落
- **「AIがシラバスから判断」には、判断のもとになりそうなシラバスの抜粋を必ず並べる。** 読む人が自分で照らし合わせられるようにする。
- **根拠:** 説明の目的は信頼を最大にすることでなく、根拠の強さに見合った信頼に合わせることにある（Google PAIR Guidebook, Explainability + Trust [9]）。推薦システムの利用者評価の枠組み ResQue [10] も、説明の分かりやすさと判断への自信を、精度とは別の項目として測っている。

### 7.3 使った情報と使っていない情報

- 並びの決め方と使った情報は、W1 では「ほかに N 科目」を開いた中の1文、W2 では一覧の最後の1文で言う。v1 の提案の見出しの下の「使った情報: 学科、選んだ方向」はやめた〔V2-05・V2-14〕。
- 詳細の最後に、使っていない情報を1文で書く。「難しさ、評判、あなたの成績は使っていません。」（v1 の見出し「この画面で使っていない情報」はやめた。時間割の重なりは v2 で使うので外した）〔V2-11〕。

### 7.4 AI の文章の扱い

- AI の回答本文は「AIの説明」として折りたたみ、提案の下に置く。カード（科目）は DB で確かめられた科目（既存の `sources`）だけから作る。
- DB で確かめられなかった科目名（既存の `unverified_codes`）はカードにしない。「確認できなかった科目名が N 件あります（提案には入れていません）」と書く。
- `notes`（検証できなかった理由）は、AI の説明の末尾に「システムからの注意」として出す。

### 7.5 並び順の説明

- 既定（おすすめ）: 「3年の多くの分野につながる順に2つと、卒業に足りない区分から1つを出しています。」（「ほかに N 科目」の中。卒業要件が入るまでは後半を除く）〔V2-05・V2-17〕。
- 興味関心: 「取る順に、1年から並べています（履修系統図）」（一覧の最後）〔V2-14〕。実装では続けて線の粗さの1文（7.6）を出す〔V2-34〕。段の中は学期→系統図の記載順（v1 のまま）。v1 の「関係の強さの順ではない」の注記〔C24〕は、v2 では画面に書かない〔V2-22〕。
- 時間割: 曜日×時限の表なので、並びの説明は要らない。v1 の「学期と系統図の線で並べています」はやめた〔V2-08〕。
- 点数・順位は出さない。

### 7.6 系統図の粗さを正直に言う

関西大学の系統図の線は、科目どうしでなく枠どうし（Neo4j の `CourseGroup` どうしの `PREREQUISITE_FOR`）を結んでいる〔T6〕。だから「枠の中のどの科目が直接の前提か」は分からない。v2 では W3 の取る順の中に「系統図の線は科目のまとまりどうしを結ぶもので、直接の前提とは限りません。」と書く（v1 は W2・W3・W4 に書いていた）〔V2-11〕。E1 は W2 に書かなかったが、実装では W2 の一覧の最後にも同じ意味の1文を書く。W4 には書かない〔V2-34〕。分からないことを分からないと言うことが、残りの情報への信頼を支える。

## 8. インタビュー・アンケートで使われることへの配慮

### 8.1 調査モード

- `mode=study` のリンクで入る。通常との違いは5つ: W9 から始まる、学科を変えられない、見出しに[使い終わった]がある（スマホも PC も〔C20〕）、終わりに W10 が出る、参加者ごとのセッション番号を端末の中で作る〔C21〕。
- 使える機能は通常と同じにする。調査のために特別に良くした画面にはしない。

### 8.2 数分で終わるようにする

- 核の導線（S1、S2-A、S3）は LLM を待たない。すべて同梱の学科データで即時に動く。
- 自由記述（S2-B）は30秒〜1分半ほどかかる（シード20科目での実測の幅。関西大学の実データでは測っていない〔T3〕）。課題に入れるかは研究者が決める（論文の主張との関係は未決 U1）。入れる場合は、待つ間も他の操作ができることを最初に伝える。
- 複数人が同時に自由記述を使うと、LLM の利用枠の上限（HTTP 429）にかかる恐れがある。時間帯を分けるか、自由記述を課題から外す。
- 通信が不安定な場所でも、核の導線は動く（学科データは最初の読み込みで端末に入る）。ただし学科データの持ち方は未決（U2）で、実行時にバックエンドから読む形（U2 の D）を選ぶと、最初の読み込みには通信が要る。

### 8.3 条件をそろえる

- 調査期間中は同梱の学科データを固定し、その版を W10 の記録に出す。
- 学科データを作り直したら版を上げる。手で書き換えない（システムの出力を評価する研究なので）。
- 比較条件（例: 系統図の線を見せる・見せない）を置く場合は、設定で W2 の段の「なぜ」、W3 の前後の枠、W4 の系統図の線を出し分けられるようにしておく（フロントだけで可能）。置くかどうかは確認事項。
- 方向のチップの並び順の影響（先頭が選ばれやすい）を避けたい場合は、既定以外の4つの順を参加者ごとに入れ替え、その順を記録に残す（P1）。

### 8.4 回答のかたより

- 参加者は、目の前の研究者が作ったものを好意的に評価しやすい。CHI 2012 の研究（インドでの450件の面接）では、中身が同じでも研究者側の物が好まれ、明らかに劣る版にしても研究者側の物が選ばれた [11]。
- 手当て:
  - W9 に「使いにくいところを見つけるのが目的」と書く。
  - アンケートは「よかったか」より、行動と具体的な判断を聞く（8.8）。
  - 好き嫌いでなく、比較を聞く（「実際に履修を決めたときと比べて」）。
  - できれば、作った本人でない人が聞き手になる。

### 8.5 1年生でない協力者

- 2年生以上には、(a)「1年の4月に戻ったつもりで」使ってもらうか、(b) 想定時点を自分の学年にして（リンクの `t=` 指定）次の科目を探してもらうか、を研究者が決めて教示する。アンケートで実際の学年を聞き、分けて集計する。
- 別キャンパスの後輩の学科に学科データが無い場合、その人には別の学科のデータで試してもらうことになり、評価の意味が変わる。扱いは確認事項。

### 8.6 個人情報と外部への送信

- アプリは名前・学籍番号を聞かない。入力欄の下に「名前や学籍番号は書かないでください」と書く。
- 自由記述は回答を作るために外部の AI サービスに送られる（今のバックエンドの設定では Gemini API）。W5 と W8 にそう書く。
- W10 の記録には、自由記述の文そのものを入れず、回数だけ入れる。アンケートの URL に入れるのは、セッション番号と集計値（数）だけ〔C22〕。

### 8.7 記録の受け渡し

- W10 に記録を表示する。中身は参加者が見て確かめられる。
- [アンケートを開く]は、セッション番号と集計値（数だけ）をアンケートの URL に事前入力して開く。名前・学籍番号・自由記述の文・科目名は URL に入れない〔C22〕。セッション番号で、アンケート・W10 の記録・インタビューのメモを結べる〔C21〕。
- アンケートの道具が事前入力に対応しないときは、[記録をコピー]でアンケートの欄に貼ってもらう（予備）〔C22〕。
- 記録の項目: セッション番号〔C21〕、調査 ID、アプリの版、データの版、端末（スマホ幅／PC 幅）、使った時間、候補に入れた科目の名前とコード〔C17〕、理由を見てから候補に入れた科目の数、詳細を開いた科目の数、原文を開いた回数、前後の枠をたどった回数、選んだ方向の順、自分の言葉で探した回数、既定の提案だけで終えたか。
- サーバーへの操作ログは作らない（K2 を増やさないため）。対面なら、画面の観察と、同意を得た録画で補う。

### 8.8 課題とアンケートの案

**課題（研究者が読み上げる例。数分の試用）**

1. 「この画面を見て、気になる科目を1つ選び、なぜ出てきたのかを確かめてください」（S1・S3）
2. 「興味に近い方向を1つ選んで、取る順番を見てください」（S2）
3. 「取ってみたい科目を候補に入れて、終わったら[使い終わった]を押してください」（S4）

**アンケート（5段階。研究の問いに合わせて Yuto が決める。下は案）**

| 項目 | 測りたいこと |
|---|---|
| 提案された科目を取るかどうか、自信を持って判断できた | 判断への自信（ResQue の decision confidence に相当 [10]） |
| なぜその科目が出てきたのか分かった | 説明の分かりやすさ |
| 先に取っておく枠と、つながる先の枠の関係が分かった | 系統図（グラフ構造）を見せた効果 |
| 出てきた理由を、シラバスの記述で確かめられた | 根拠の確認 |
| 選択式: 今日、候補を決めるときにいちばん重く見たこと（内容への関心／前後のつながりや順番／楽さ／友達と同じ／時間割／その他） | 選ぶ理由の中身 |
| 選択式: 実際に履修を決めたとき、いちばん重く見たこと（同じ選択肢） | 上との比較（上級生は過去の実際） |
| 自由記述: 使いにくかったところ、迷ったところ | 改善点 |

**観察（研究者が記録）:** 最初に何をしたか、迷った箇所、研究者が助けた回数、声に出した疑問。

## 9. バックエンドに新たに求める機能の一覧

### 9.1 結論

**新しい API: 0。任意の改善: 1（B1）。**

ただし、学科データの受け渡し（9.2 の D1〜D3）にはデータ側の作業が要り、その JSON はリポに無い（`ingestion/.gitignore` の著作権の方針で除外。持ち方は未決 U2）〔T2〕。自由記述には E1（エージェントの関西大学データへの対応）が要り、origin/main にはまだ無い〔T4〕。コンペの審査では、この2つを数えて K2 = 2 とされた〔ED1〕。

学科1つ分の系統図（21枠・70科目・25本）とその科目のシラバスは小さい（数百 KB 程度）。これをフロントに同梱し、既定の提案・方向・取る順・前後の枠をフロントで計算する（同梱の仕方は未決 U2）。LLM が要るのは自由記述だけで、そこは既存の `POST /test/agent/mcp` をそのまま使う。

この判断のトレードオフ（入口に LLM の出力を使わないことと、論文の主張との関係）は未決 U1 として、2026-11-04 の MTG で Yuto に確認する（10.3 の Q1）。

### 9.5 任意の改善 B1: 自由記述の回答に、科目ごとの理由を構造化して付ける

- **目的:** F6（本文の見出しで区切る）は書式に頼るので崩れやすい。B1 が入れば W5-3 の「なぜ」が安定する。入らなくても M3 の導線は F6 と W3 で保てる。
- **対象:** `POST /test/agent/mcp` の応答。
- **追加する項目（案）:**

```python
class ProposalItem(BaseModel):
    code: str                     # DB で確かめられた科目コードのみ
    reason: str                   # 日本語1文、60字以内。「なぜこの科目か」
    evidence_excerpt: str = ""    # 判断のもとにしたシラバスの文（シラバス本文に含まれる文字列）
    order: int | None = None      # 取る順（1 が先）。決められなければ None

# McpAgentRunResult に items: list[ProposalItem] を足す
```

- **受け入れ基準:**
  - Given 自由記述の質問 When 回答が返る Then `cited_codes` のうち DB で確かめられた科目ごとに `items` が1件ずつある
  - `reason` は空でなく60字以内
  - DB に無いコードの item は返さない（既存の `attach_sources` と同じ検証で `unverified_codes` に回す）
  - `evidence_excerpt` が空でなければ、その科目のシラバス本文に含まれる文字列であることを機械的に確かめる。含まれなければ空にして `notes` に書く
- **流用できるもの:** 静的経路の `Candidate.reason` と `Evidence`（`course_core/schemas/traversal.py`）の考え方。

### 9.6 B1 が無いとき・データが遅れたときの縮退

| 状況 | どうなるか |
|---|---|
| B1 が無い | 自由記述の「なぜ」は F6 で本文から取り出す。取り出せない科目は全文へのリンク |
| E1 が調査に間に合わない | 自由記述を出さない。S1・S2-A・S3・S4 はすべて動く。S2-B だけが使えない |
| E2 が無い | 学科データの `detail_url` を使うので、学科の科目は原文に届く |
| D1・D2 が調査に間に合わない | 入口の提案が作れない。10.1 の R1（受け渡しの方法は未決 U2） |

| 1 システム状態の可視化 | 待ちの経過時間・目安・中断、候補の件数、選択中の方向、使った情報 | 系統図からの提案と AI の提案の区別が一目で分かりにくい。「根拠の種類」と「使った情報」で補う（1） |

| 7 柔軟性と効率 | 自由記述、PC の常設入力欄、行から直接[候補に入れる] | 科目名で直接探す手段が v0 に無い（2。P1） |

| 9 エラーの認識・診断・回復 | W6 のどの案内も、原因と次の行動を書く | なし |
| 10 ヘルプとドキュメント | このAIについて、科目ごとの根拠の種類、使っていない情報 | なし |

## 11. この UX がうまくいったかを測る指標

### 11.1 いちばん見たい指標

**理由を確かめてから候補に入れた参加者の割合** = 詳細（W3）を開いたあとで、その科目を候補に入れたことが1回以上ある参加者の数 ÷ 参加者の数。

「楽さや友達でなく、理由を見て選んだ」行動にいちばん近い。W10 の記録の「理由を見てから候補に入れた科目」から数える。

v2 では一覧の＋から詳細を見ずに候補に入れられ、詳細は行を押して開く。v1 の画面（カードの主の操作が［理由と出典］）より、この割合は下がりうる。v1 と v2 の値を比べるときは、画面の違いを書き添える〔V2-10〕。

### 11.2 行動の指標（W10 の記録と観察から）

| 指標 | 定義・計算式 | 目安（調査の前に確定する案） |
|---|---|---|
| 最初の提案までの操作数 | 最初の画面から、提案が見えるまでの操作の数 | 0（設計値。観察で確かめる） |
| 最初の提案までの時間 | リンクを開いてから1件目の提案が表示されるまでの秒数（画面の記録） | 2秒以内 |
| 根拠の確認率 | 詳細を1回以上開いた参加者 ÷ 参加者 | 60% 以上 |
| 原文の確認率 | シラバス原文を1回以上開いた参加者 ÷ 参加者 | 記録するだけ（目安なし） |
| 系統図をたどった率 | 前後の枠や枠の科目を1回以上たどった参加者 ÷ 参加者 | 40% 以上 |
| 候補に入れた率 | 候補に1件以上入れた参加者 ÷ 参加者 | 70% 以上 |
| 既定依存率 | 候補が既定の提案の科目だけで終えた参加者 ÷ 候補に入れた参加者 | 50% 以下 |
| 方向を選んだ率 | 方向を1回以上選んだ参加者 ÷ 参加者 | 記録するだけ |
| 課題の成功率 | 8.8 の課題を研究者の助けなしで終えた数 ÷ 課題の数 | 80% 以上 |
| 待ちの中断率 | 自由記述のうち、結果が出る前に中断・離脱した数 ÷ 送った数 | 記録するだけ |
| 範囲外の質問の数 | W6-1 が出た回数 | 記録するだけ |
| 端末の差 | スマホと PC の課題の成功率の差 | 10ポイント以内 |

### 11.3 アンケートの指標

8.8 の各項目の分布（中央値と人数）。「今日いちばん重く見たこと」と「実際に履修を決めたときにいちばん重く見たこと」の組み合わせの集計（例: 実際は「楽さ」だった人が、今日は「内容への関心」や「つながり」を選んだ人数）。

### 11.4 判定のしかた

- 参加者は多くても数十人の見込みなので、割合だけでなく「x / n 人」で書く。
- 目安は調査の前に決めて記録し（事前登録）、あとから変えない。リポの `docs/experiments/` の書き方（目的・仮説・環境・手順・結果・限界）にそろえる。
- この章の目安は UX の出来を見るためのもので、論文の仮説（グラフ構造の効果）の検定とは分ける。
