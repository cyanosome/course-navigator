## 1. 目的と問い

10/7 の MTG で、Yuto が Discord に書いた TODO のうち Aki_Ha の分に次の3つがあった（ほかに「ノードを洗練する」があり、これは [ノード設計比較](2026-10-11_node-design-comparison.md) で扱った）。

- Test3-? のページを作り、adk web でしか見られないエージェントの回答をテストページで見られるようにする
- 回答のソース（出典）を見えるようにする
- 今は Neo4j しか見ていないので、回答の前に RDB で詳細を確認させる

これを PR #14（`dev/akiha_test3-2` → `test/agent-communication`）で実装した。PR #14 の単体テストは LLM と PostgreSQL を偽物に置き換えている（`backend/tests/test_mcp_grounded.py`）。本物の Gemini と本物の DB をつないだときに動くかは、単体テストでは分からない。そこで次の問いを確かめた。

1. 実際の API で、エンドポイントが route=mcp のまま最後まで回答を返すか（例外やタイムアウトで止まらないか）
2. エージェントが Neo4j の MCP ツール（`read-cypher`）と RDB ツール（`get_course_details`）を実際に呼ぶか
3. `attach_sources` が返す `sources` と `unverified_codes` が DB の中身と合っているか
4. 回答の中身（科目の関係・担当教員・開講時期）がシードと一致するか（手で確かめた範囲）
5. 既存の静的エンドポイント `POST /test/agent` が今までどおりの形で応答するか

あわせて、MCP サーバーを起動できないときに LLM を動かさず静的経路へ倒れるか（PR #14 の 32f87f5 で入れた処理）も、別のスクリプトで1回確かめた（付録の (d)）。

## 4. データ

## 5. 対象（処理の流れ）

```
POST /test/agent/mcp {"question": ...}
  └ run_mcp_grounded（backend/src/agent/runner.py）
      ├ 事前接続: エージェントの各ツールセットで get_tools() を呼ぶ（ここで MCP サブプロセスが起動する）
      │    失敗した・0件だった → LLM を動かさず静的 DAG で回答（route="static"、notes に理由）
      └ ワークフロー（build_mcp_grounded_workflow、backend/src/agent/workflow.py）
          START → route_initial ─ mcp ──→ mcp_agent ──→ attach_sources → 応答
                               └ static → parse_intent → …（既存の静的 DAG）
```

- `route_initial`（`backend/src/agent/nodes.py`）: `AGENT_ENABLE_MCP` が有効で `GEMINI_API_KEY` があれば mcp に進む。
- `mcp_agent`: ADK の LlmAgent（`build_grounded_mcp_agent`、`backend/src/agent/mcp_agent.py`）。
  - ツール: Neo4j の MCP ツール（今回呼ばれたのは `read-cypher`。LLM が Cypher を書いてグラフを読む）と、`get_course_details`（`backend/src/agent/rdb_tools.py`。科目コードを受け取り、PostgreSQL から担当教員・開講時期・単位数・本文を返す。1回20件まで）。
  - プロンプト: 共有プロンプト `backend/src/agent/prompts/compose_answer.md` に、RDB の手順を書いた `grounded_addendum.md` をつなげたもの。
  - 出力: `answer`（回答文）と `cited_codes`（言及した科目コード）。ADK が構造化出力のために `set_model_response` というツールを差し込み、LLM はこれを呼んで最終回答を返す。
  - どのツールを何回呼ぶかは LLM が決める。
- `attach_sources`（`backend/src/agent/nodes.py`、中身の純関数は `backend/src/agent/grounding.py`）: LLM を使わない。`cited_codes` を正規化（NFKC で半角にそろえ、前後の空白と `[]` `【】` を外し、重複を除く）してから PostgreSQL で引き直し、行があったコードは `sources`（DB の行から作った出典）に、無かったコードは `unverified_codes` に入れる。

比較のため、既存の `POST /test/agent`（`run_course_navigator`、静的 DAG、LLM 0回）にも Q1 を1回送った。

## 6. 手順

1. 有料枠のキーを `.env` に入れ、`docker compose up -d --force-recreate backend` で backend を作り直した（23:21）。
2. 起動が終わる前に Q1 を送って接続を拒否された（付録の (e)）。起動の完了をログで確かめてから、次の2つのコマンドを順に流した（リポのルートで。スクリプトは当時 `e2e_mcp.py` という名前の一時ファイルで、中身は `backend/eval/e2e_test3_2.py` の docstring 以外と同じ）。

```sh
# Q1（23:28:16）
docker compose exec -T backend python - 1 600 < e2e_mcp.py 2>&1 | grep -v '^JSON' | cut -c1-400

# Q2 → Q3 → 旧エンドポイント（23:30:21）
for q in 2 3 old; do
  docker compose exec -T backend python - $q 600 < e2e_mcp.py 2>&1 | grep -v '^JSON' | cut -c1-300
done
```

- 各問1回だけ、1つずつ順に送った。やり直しはしていない。
- `grep -v '^JSON'` で、応答全体を1行にした JSON 行を表示から除いた。`cut -c` で各行を 400 バイト（Q1）または 300 バイト（Q2 以降）で切った。このため、応答の全文は保存されていない（11. 限界）。
- 予算の上限は設けていない（手で1問ずつ流した）。

再現するには:

1. AGENTS.md の手順で proxy・db・backend を起動する。`.env` に `GEMINI_API_KEY`（無料枠は1日20リクエストで足りないので有料枠）と DB のパスワードを入れる。`AGENT_MODEL` と `AGENT_ENABLE_MCP` は指定しない（既定で gemini-3.8-flash、MCP 有効）。
2. コードを `ca94e4a` 以降（PR #14 を含む版）にする。
3. `docker compose exec -T backend python - all 600 < backend/eval/e2e_test3_2.py` を流す（`all` で Q1〜Q3 と旧エンドポイントを順に送る）。全文を残したいときは `grep` と `cut` を付けない。

## 7. 指標の定義

| 指標 | 定義 |
|---|---|
| status | HTTP ステータスコード |
| wall_ms | スクリプトがリクエストを送ってから応答を読み終えるまでの時間（ミリ秒）。スクリプト側で測る |
| latency_ms | サーバー側の `run_mcp_grounded` が測る時間。事前接続（MCP サブプロセスの起動を含む）からワークフローの終了まで。ツールセットの終了処理（MCP サブプロセスを止める時間）は含まない。wall_ms − latency_ms は、ツールセットの終了処理と HTTP・FastAPI の処理にかかった時間 |
| route | 実際に通った経路。mcp（LLM + MCP）か static（静的 DAG） |
| ツール呼び出し | ADK のイベントに含まれる function_call を呼ばれた順に並べたもの。この記録で回数を数えるときは `set_model_response`（最終回答を返すための ADK のツール）を除く |
| cited_codes | LLM が回答で言及したとして返した科目コード（attach_sources の正規化の後） |
| sources | cited_codes のうち PostgreSQL に行があったもの（DB の行から作った出典） |
| unverified_codes | cited_codes のうち PostgreSQL に行が無かったもの。\|unverified\| = \|cited\| − \|sources\| |
| LLM リクエスト数（推定） | この確認では数えていない。後で同じエージェント構成を流したノード設計比較では、M1・M2 の28実行すべてで「LLM リクエスト数 = ツール呼び出し数（set_model_response を除く）+ 1」だったので、それに当てはめた推定値を参考に書く |
| 中身の正しさ | 保存された範囲の回答文と cited_codes を、`backend/seed/courses.json` の該当行と手で突き合わせた |

計算の例（Q3）:

- cited_codes = [GMS-302, GMS-201, GMS-402]。3つとも `test_postgres_syllabus` に行があるので sources は3件、unverified は 3 − 3 = 0。
- wall_ms − latency_ms = 54,686 − 53,243 = 1,443 ミリ秒（ツールセットの終了と HTTP の処理）。
- ツール呼び出しは read-cypher → get_course_details → read-cypher の3回（set_model_response を除く）。LLM リクエスト数の推定は 3 + 1 = 4 回。

列の意味:

- latency_ms と wall_ms は7節の定義どおり。Q1〜Q3 の node_sequence はどれも `route_initial → mcp_agent → attach_sources` で、notes は空だった（静的経路への切り替えは起きていない）。

### 8.3 気づいたこと

- Q1 は曖昧な問いである。MCP エージェントの最初の Cypher は科目名に「データサイエンス」を含む科目を探すもので、シードではこれに GMS-301 と GMS-401 の両方が当たる。エージェントは聞き返さずに GMS-301 を起点と決めて答えた。静的 DAG（旧エンドポイント）は同じ問いを曖昧として聞き返した。
- 時間: Q1 は 92.6 秒で、LLM 推定10回で割ると1回あたり約9秒。約40分後に流したノード設計比較では、ほぼ同じ問い（q14）を同じ構成（M2）で流して LLM 9回・30.5 秒だった（1回あたり約3.4秒）。差の原因は調べていない（API 側の混み具合などが考えられるが、測っていない）。

## 10. 考察

言えること:

- PR #14 の経路は、実際の Gemini API と実際の DB で、3問とも例外なく最後まで動いた。Neo4j の MCP ツールと RDB ツールの両方が実際に呼ばれ、出典はすべて DB の行から作られた（1・2・3の問いに「はい」）。
- 保存された範囲で手で照らした事実はシードと一致した（4に「はい」。範囲は限られる）。
- 旧エンドポイントは今までどおりの形で応答した（5に「はい」）。

言えないこと:

- 回答の正確さや網羅性。3問を1回ずつ流しただけで、正解の集合を前もって決めておらず、照合も保存された範囲に限られる。golden 14問で4つの設計を比べたものは [ノード設計比較](2026-10-11_node-design-comparison.md) にある。
- 出典の検証が誤った引用を捕まえられること。今回は unverified が0件で、捕まえる対象が無かった。DB に無いコードを unverified に回す動きは、偽モデルを使った単体テスト（`backend/tests/test_mcp_grounded.py`）で確かめている。
- 速度の一般的な水準。53〜93 秒はこの時刻の1回ずつの値で、約40分後の実行では同じ構成のほぼ同じ問いが3分の1ほどの時間で終わった（8.3）。

## 11. 限界

- 3問、各1回。LLM は温度が API の既定値のままで、同じ問いでも結果は揺れうる。
- データはシードの20科目だけ。駒澤大学のデータ（Neo4j のスキーマがシードと違う）では確かめていない。
