## 7. 指標の定義と計算式

### 7.1 必須の条件

### 7.2 W1 の情報量（改訂コンペと同じ定義。`measure.py`）

- CL1: W1 の最初の表示（ビューポート 0〜812px）に見えている文字の数。テキストノードの字（空白・改行を除く）を数える。入力欄の placeholder や `::before` の content はテキストノードでないので数えない（測定スクリプトの「実装で決めたこと」17。数えなかった字は `W1.diagnostics.cl1NonTextList` に出る）。
- CL2: 最初の表示に見えている「強調された要素」の数（直下の字の font-weight が 600 以上の要素と、地の色が透明でも「ほぼ白」でもない要素の和集合）。
- CL3: 最初の表示に見えている文字を持つ要素の、(font-size, font-weight, color) の組の種類の数。
- 増分 = その案の値 − entry=0 の値。

### 7.3 順位と合計

- 審査役の順位: 観点ごとに4案へ1〜4位（同点なし）。平均順位 = J1 と J2 の順位の平均。
- CL1 の増分の順位: 増分が小さいほど上。同じ値の案には平均順位を付ける（3案が1位で並べば、各 (1 + 2 + 3) ÷ 3 = 2 位）。
- 合計 = 2 × (a) の平均順位 ＋ (b) の平均順位 ＋ (c) の平均順位 ＋ CL1 の増分の順位。小さいほど良い。同点は (a) が上の案。
- 感度分析（審査の前に決めた。判定には使わない）: CL1 に、見えている入力欄の placeholder の字（`cl1NonTextList` の kind = placeholder の字数）を足した値で増分と順位を出し直す。

**計算の例（a）:** (a) は J1 1位・J2 1位で平均 1。(b) は J1 3位・J2 4位で平均 3.5。(c) は J1 1位・J2 1位で平均 1。CL1 の増分は 0 で、0・a・b の3案が並ぶので 2位。合計 = 2 × 1 + 3.5 + 1 + 2 = 8.5。感度分析では、a の CL1 は 189 + 14 = 203、増分 +14 で b と並んで 3.5位になり、合計 = 2 × 1 + 3.5 + 1 + 3.5 = 10。

## 10. 考察

### 10.1 a の勝ちは、どこまで揺れにくいか

- a の勝ちは、重みが2の (a) と、(c) で決まった。2人とも (a) と (c) で a を1位にし、2人の順位はこの2つの観点で完全に一致した。(b) では a は 3.5位で、むしろ不利だった。
- CL1 に placeholder の字を足すと、a の CL1 の増分の順位は 2 から 3.5 に下がるが、合計は a 10・0 13・b 13・c 14 で a のまま。審査役1人ずつでも a（J1 だけ 8、J2 だけ 9）。1人ずつかつ placeholder 込みでも a（J1 だけ 9.5、J2 だけ 10.5。この報告での計算）。
- 事前登録外の確かめとして、(a) の重みを1にした単純な和（(a) + (b) + (c) + CL1 の増分の順位）でも、a 7.5・b 9.5・0 10・c 13 で a が最小（この報告での計算）。
- 2位以下は揺れる。主では b 11.5・0 14 だが、placeholder 込みでは 0 と b が 13 で並ぶ。

ただし、どの値も見本1回・審査役各1回の判定で、ばらつきは測っていない。「この4案の画像の中では a が入口として分かりやすい」までは言えるが、「a の形が利用者にとって最も使いやすい」とは言えない。

### 10.2 (b) で今の形が1位だったことの読み方

(b)「画面がうるさくならない」では、2人とも 0 を1位にした。W1 で増えたものが無いので当然でもあるが、W5 では 0 にだけ［探す］が無い（4.3）。この差は (b) で 0 を有利にしうる。一方で、2人とも 0 の W5 について「送り方が分からない」と書いており、ボタンが無いことは (b) では得でも、使い方の分かりやすさでは損になっている。［探す］は UX 仕様 W5-1 にあるボタンで、今の実装に無いのは仕様との差である。入口の置き方とは別に、実装に［探す］を足すかどうかを決める必要がある（提案。まだ何も変えていない）。

### 10.3 CL1 は「枠が1つ増える」ことを測らない

a と b は W1 に枠（a は高さ 48px の欄、b は 64px の帯）を足したが、`measure.py` の CL1・CL2・CL3 はどれも増えなかった。CL1 は placeholder を数えず、CL2 は地を塗らない枠を数えず、CL3 は例文を既存の「14px 灰」の書式にそろえたので増えない。改訂コンペで作った物差しは「字・太字・色地・書式」の量を測るもので、枠や帯のように面積を取る要素の追加は拾えない。今回の判定では、この部分は審査役の (b) に任された。placeholder を足した感度分析は、字の分だけを補ったものである。

### 10.4 a を実装するときに考えること

審査役2人が挙げた a の気がかり（8.5）を、実装のときに考える。

- 一番上の虫めがねの欄が、普通の科目名検索に見えやすい。AI に頼めるという説明は、書き始めるまで出ない。
- 一覧が 64px 下がる（1件目の行の下端 312px → 376px）。
- W5 で、注意・［探す］・チップが上にたまり、一覧が大きく下がる。
- 書いている間も「おすすめ」が選ばれたままで、絞り込みと掛け合わされるのかが紛らわしい（J2）。

ほかに、作り手が3案に共通の弱みとして挙げた点がある（`entry.md` の「気になっている点」）。例文が placeholder なので書き始めると消え、見えるラベルが無い（E1 からの弱み。WCAG 3.3.2）。例文から「科目名」を外したので、科目名でも探せることが画面から読み取れない。PC の上の帯から検索欄が無くなるので、右上に検索を探す人は見つけられない。

### 10.5 審査役の一致と系統

2人の順位は12セル中10セルで一致した。作り手は Claude の系統で、J1 も同じ系統だが、別系統の J2 もほぼ同じ順にしたので、今回のデータからは同系統びいきは読み取れない。各セル1回なので、無いとも言えない。

### 10.6 このコンペで分からないこと

利用者（1年生や調査の協力者）は1人も見ていない。学生が実際に自分の言葉で書くのか、書いた文で AI の答えに満足するのかは、このコンペでは分からない。キーボードが出たときの見え方（特に b と、高さ 667px の端末での c）、入口を押したときの動き、送ったあとの待ちの表示も見ていない。

## 付録: 試行錯誤の経緯

- **J1 の答えのファイル:** J1 の答えはファイルになっておらず、監査役が会話の中の全文を転記した。その転記の末尾に `}` が1つ多く、JSON として読めなかったので、この報告を書いた実行役がその1字だけを外して `j1/answer.json` に保存した。順位・理由・気がかりの中身は変えていない。

- **PC の見本の1行の直し:** b の欄を列の下に固定するため、作り手が E1 の見本の高さの指定を1行直した（4.1）。4案に同じく効く。
