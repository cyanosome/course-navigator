## 1. 目的と問い

UX 仕様（[`docs/frontend/ux-spec.md`](../frontend/ux-spec.md)、確定版 v1）は画面の構成と文言を決めたが、書体・色・装飾は「次の段階のデザインシステムで決める」として扱っていなかった。作り直しのフロントエンド（React 19 + Vite + TypeScript）の見た目を決める前に、土台を1つ選びたい。依頼主（Aki_Ha）は、AI がよく使う見た目（定番の書体、クリームやテラコッタ、紫のグラデーション、どこにでもある角丸カードと柔らかい影など）を「Claude らしさ」が前に出るとして強く避けたい。そこで、避けるものを禁止リストと検証ツールで機械的に判定できるようにし、作り手を変えた3案を同じ課題で独立に作らせ、事前に決めた基準で選ぶことにした。フロントエンドの作り直し（ブランチ `dev/akiha_frontend`）の、UX コンペ（[2026-11-03_frontend-ux-competition.md](2026-11-03_frontend-ux-competition.md)）に続く段階にあたる。

知りたかったこと:

1. 3案のうち、どれを土台にするか。事前登録の規則だけで決まるか
2. 禁止リストの道具（機械）と、スクリーンショットを見る審査役（人の代わりの AI）の判定は食い違うか
3. 2人の審査役の順位はどのくらい一致するか。UX コンペで疑われた「審査役が同じ系統のモデルの案を甘く見る」傾向は出るか

### 4.3 偏り

- **作り手と審査役のモデルが重なる。** alpha・beta は J1 と同じ Opus、gamma は J2 と同じ Gemini 4 Argon (High)。作者は伏せたが、見た目の癖で同じ系統の案が分かる恐れはある。
- **作り手の条件がそろっていない。** alpha・beta は道具を使って、測り、撮り、フォントをサブセットにし、直すことを自分で繰り返せた。gamma は読むことしかできず、検証と撮影は運び役が行い、直しは1回（必須の不合格の箇所だけ）だった。フォントのファイルも、依頼文が「運び役が公式の配布元から置く」としたため、gamma は配信の形を自分で作れなかった。
- **禁止リストの根拠の一部は、alpha・beta が使ったスキルそのもの。** hallmark（根拠 E06〜E10）と taste-skill（E11）。どちらも、何が禁止かを知っている状態で作った（禁止リスト自体は3案とも読んだ）。
- **見本のサンプルの影響。** 3案とも依頼文で `tests/` のサンプルを書式の例として見た。そのサンプルの書体は BIZ UDPGothic で、色の一部と角丸・動きの値を gamma がそのまま使った（10.3）。
- 各案は1回ずつしか生成していない（gamma は直しを含めて2回の呼び出し）。

## 6. 手順

1. 監査役のセッションで、禁止リスト（`banlist.md`・`banlist.json`）と検証ツール（`check_banlist.py`・`check_contrast.py`・`check_font.py`・`colorlib.py`）、書体の見本ページ（`specimen.html`）、テスト（`tests/`）を用意した。`tests/run_tests.py` で 24 項目すべて合格（フォントの確認を含む）。
2. 3つの作り手に依頼文を渡した。alpha・beta は Claude Code のサブエージェントとして、検証ツールを自分で走らせながら DESIGN.md・specimen.html・fonts・checks.txt・撮影を作った。
3. gamma: 運び役が agy を呼んだ。最初の試行は、読み取りの許可が headless では出せずに自動で拒否され、出力なしで終わった（無効。付録）。1回目（返答 71,611 字。result イベントの所要 791.7 秒、入力 148,339・出力 73,071〈うち思考 40,639〉トークン）の成果物に、運び役がフォントを置き、検証ツールを走らせ、撮影した。禁止が2件（P17 と C03）出たので、2回目（直し）を依頼した（返答 71,601 字。result イベントまで 273.9 秒、入力 60,510・出力 33,800〈うち思考 2,581〉トークン）。2回目で禁止は 0 件になった。agy のプロセスは2回目の result イベントの後も終わらず、1,845.1 秒後に終了コード 4294967295 で終わった（原因は調べていない。返答は result イベントから取れた）。
4. 審査の補助が、DM4 を3段階の読み（L1〜L3）で数え、K2 を Edge と Chrome で実測し、check_banlist と check_contrast を3案に走らせ直した（`dm4-k2.md`）。
5. 監査役が撮影を盲検の名前でコピーし、J1 と J2 に別々に渡した。J2 は agy で1回だけ呼んだ。
6. 監査役が集計した。3案とも DM4 を満たさなかったので、事前登録外の判断で alpha を土台にした（9節）。
7. 実行役のサブエージェントが、alpha を土台に確定版（`docs/frontend/DESIGN.md`）と確定版の見本を作り、配信するフォントを `frontend/public/fonts/` に置いた。審査で見つかった問題の解消（F1〜F6）、DM4 の欠けの補完と配信の方針（D1〜D6）、UX 仕様の文の直し（S1）は、DESIGN.md の変更履歴にある。

## 10. 考察

### 10.1 alpha を選んだ判断は、どこまで揺れにくいか

以下はこの報告で計算した感度で、事前登録外である。

- **DM4 の読み:** L3 で読めば alpha だけが DM4 を満たし、事前登録の規則そのままで alpha になる。DM4 を外して順位の合計だけで見ても alpha。どの読みでも、alpha 以外が選ばれる道は無い。
- **K2 の差:** alpha と beta の差は 3,392 B（alpha の約 5%）で小さい。仮に K2 の順位が入れ替わっても、合計は alpha 5・beta 5 の同点になり、同点の規則（K3 が良い方）で alpha になる。
- **K3 の審査役:** J1 だけなら alpha 1.33・beta 1.67・gamma 3.00、J2 だけなら 1.00・2.00・3.00 で、どちらも順は同じ。

ただし、どの値も各案1回の生成・各審査役1回の判定で、ばらつきは測っていない。「この3案の中では alpha が土台として妥当」までは言えるが、「alpha の作り方（Opus 5.5＋hallmark）が他より良い」とは言えない。

### 10.2 alpha と beta が同じ書体に行き着いた

alpha と beta は、別のセッション・別のスキルで、どちらも M PLUS 1p の 400・700 に行き着いた。比べ方は違う（alpha は 14px・1倍の画素の差 D = Σ|a−b| ÷ (Σa + Σb) で候補4つ、beta は 48px の d = 1 − IoU で候補8つ）。どちらも事前に「BIZ UDPGothic が字の見分けやすさの指標で1位」と予想して外れ、BIZ UDPGothic の「ぱ／ば」の差が M PLUS 1p より小さいことを見つけた。配信も、どちらも見本の字だけのサブセットと unicode-range の組み合わせだった。

測り方の違う2つの比較が同じ書体を選んだので、「M PLUS 1p が濁点の見分けと軽さで有利」という結果は、1つの指標の作りものではなさそうである。ただし、2案は同じモデル（Opus 5.5）で、同じ禁止リスト（M PLUS 1p は「根拠なし」で禁止にしていない）と同じ README を読んでいる。独立なのはセッションとスキルだけで、モデルの好みが共通している可能性は分けられない。どちらの比較も画素の差という代わりの指標で、1年生に読ませた実験ではない。

### 10.3 gamma は見本の値と Tailwind の既定色を使った

審査の補助の照合（`dm4-k2.md` の3章）によると、gamma は書式の例として渡した `tests/good/DESIGN.md` の色3つ（surface #F2F5F3、ink #1C2422、primary #0A7C86 を evidence-graph-border に）を同じ値で使い、書体（BIZ UDPGothic）、部品の角丸 6px、動き（120ms・cubic-bezier(0.2, 0, 0, 1)）も見本と同じだった（120ms と cubic-bezier は alpha と beta も使っている）。27色のうち8色が Tailwind v3 の既定パレットと同じ値だった（amber-100・yellow-700・blue-600・sky-100・sky-900・sky-600・red-600・blue-700）。

どれも禁止リストの文言では禁止に当たらない。P21（要注意）は Tailwind の既定パレットの「クラス」を拾う項目で、hex の値は対象外。紫の禁止（C04・P05）は色相の門で青を外している。見本と同じ値を禁じる項目は無い。したがって K1 は 0 で、禁止リストの道具では差がつかなかった。

gamma が値をそのまま使った理由は分からない。道具を走らせられない条件で、見本の値なら通ると見込んだ可能性はある（推定。確かめる方法が無い）。依頼主の要望（「AI がよく使う配色を使わない」「理由を検証してから採用する」）の趣旨から見れば、既定パレットや見本の値の流用は避けたいものなので、次に禁止リストを使うときは、Tailwind の既定パレットの hex と、配った見本の値を要注意に足すことを提案する（この報告では変えていない）。

### 10.4 審査役の一致と、同じ系統への甘さ

- 2人の順位は9セル中7セルで一致し、違いは (c) の alpha と beta だけだった。UX コンペで重大度の数が審査役の間で大きく食い違ったのと比べると、順位を付ける形式・観点3つ・画像6枚だけ、という今回の形では一致が高かった。
- Gemini の J2 は Gemini 製の gamma を全観点で最下位にした。UX コンペで見えた「審査役が同じ系統を甘く見る」傾向（UX コンペの報告でも可能性の段階）は、今回は見えなかった。Claude 系の J1 が Claude 系の alpha・beta を上位にしたことは同系統びいきとも矛盾しないが、別系統の J2 も同じ順にしたので、今回のデータからは同系統びいきは読み取れない。各セル1回なので、無いとも言えない。
- gamma の順位の低さは、モデルの違いだけでなく、作り手の条件の違い（道具なし・直し1回・フォントの配信の形を自分で作れない）も反映している。比べたのは「モデル」ではなく「作り手の構成」である（UX コンペの 10.3 と同じ）。

### 10.5 道具と審査役の食い違い

J1 は beta（案3）の AI の区画について「桃色の地とオレンジの点線は…クリーム・テラコッタ系に寄っている」と書いた（`k3-j1.md:31`、`:56`）。禁止リストの道具は、beta に禁止も要注意も出していない。道具は禁止の色の見本との色差で判定するので、見本から離れた「似た印象の色」は拾えない（`banlist.md` の8章の限界）。機械の判定は必要条件の確認にとどまり、見た目の印象は審査役の目で見るしかない、という分担が今回も当てはまった。

逆に、gamma の1回目の禁止2件は、どちらも DESIGN.md の文の中で禁止のものに触れた箇所だった（「`transition: all` はすべて使わない」の文が P17、「C03 `#788c5d` から ΔE00>18」の文が C03）。使っていないものを拾った例で、2回目は文の言い回しを変えただけで 0 件になった。道具は Markdown の本文に書いた名前や色も拾う仕様で（README の限界）、「使わない」と書く行には `banlist:allow` を付ける決まりがある。gamma はこの決まりを使わなかった。

### 10.6 K2 の値の意味

alpha の ui と beta の core は、どちらも見本のページに出る字から作ったサブセットである。最初の表示が軽いのは見本のページでの話で、本番の画面では科目名や枠の名前の字が ui に無いため、予備のファイル（rest）が読まれる（確定版の DESIGN.md の 2.4.1）。本番での最初の表示の重さは未測定で、alpha と beta の 3,392 B の差は、本番の字の集合しだいで簡単に入れ替わりうる。gamma は、Google Fonts の分割配信を使ったとしても最初の表示で 727,360〜980,796 B という見積もり（運び役の `slice_estimate.py`。審査の補助は測り直していない）で、どの数え方でも3位は変わらない。

### 10.7 DM4 は壊れやすい基準だった

DM4 は3案とも落ちる結果になり、規則で土台を決められなかった。原因は、(1) 「すべての決定に」「節番号つき」を文言どおりに数えると1件の欠けで落ちる、(2) 何を「節番号」「検証」と数えるかの細部が事前登録に無く、応募作を見たあとで決めた、(3) gamma は依頼文で「検証の観点」を求められ、道具を走らせられなかった、の3つと考える。次に同じ形で比べるなら、DM4 の数え方（認める節番号の範囲、検証の結果まで要るか）を事前登録に書き、作り手の道具の条件をそろえるか、条件の違いを前提にした基準にする。

### 10.8 このコンペで分からないこと

見た目を決めたのは、DESIGN.md と見本とスクリーンショットを AI が判定した結果で、利用者（1年生や調査の協力者）は1人も見ていない。「1年生が安心して読める」かは、このコンペでは分からない。確定版で入れた変更（F1〜F6、D1〜D6）は、審査役にもう一度見せて確かめてはいない。

## 11. 限界

- 応募作は3案・各1回の生成（gamma は直しを含めて2回の呼び出し）、審査役は2人・各1回。生成と判定のばらつきは測っていない。
- 作り手の条件（道具、直しの回数、フォントの配信の形、スキル）がそろっていない（4.3）。
- 作り手と審査役のモデルが重なる（J1 と alpha・beta、J2 と gamma）。
- 禁止リストの根拠の一部が、alpha・beta が使ったスキルそのもの（4.3）。

## 付録: 試行錯誤の経緯

- **gamma の最初の試行（無効）:** agy は headless の実行で読み取りの許可を求める画面を出せず、ファイルの読み取りが自動で拒否されて、出力なしで終わった（18:15:39〜18:16:01）。運び役のスクリプトも、result の形の違いで落ちた。その後の2回は read_file でファイルを読めた。今の `run_agy.py` には `--add-dir`（リポの `docs/frontend`）があるが、最初の試行のときの引数は残っていない。
- **gamma の1回目で禁止2件:** どちらも DESIGN.md の文の中で禁止のものに触れた箇所だった（10.5）。2回目の依頼文は「検証で出た問題だけを直し、それ以外は一字も変えない」と指示し、gamma は該当の2行だけを書き換えた（1回目と2回目の DESIGN.md の差は2行。見本は変わっていない）。
- **agy のプロセスが終わらない:** 2回目は result イベント（273.9 秒）のあとも agy が終わらず、1,845.1 秒後に終了コード 4294967295 で終わった。返答は result イベントから取れた。原因は調べていない。
- **J2 の入力の切れ:** UX コンペでは agy への長い入力が黙って切れた。今回の J2 は画像6枚を read_file で開いたことが実行ログで確かめられ、記録の最後にも「6枚すべてを開けた」とある。
- **作者名の記載:** gamma の依頼文は「成果物に自分の名前・モデル名・ツール名を書かない」と指示した。beta の DESIGN.md の0章には、使ったスキルの名前（taste-skill）が出ている。審査役 J1・J2 は画像だけを見たので、盲検には影響していない。審査の補助は案の名前（alpha・beta・gamma）でファイルを見ており、盲検ではない。
