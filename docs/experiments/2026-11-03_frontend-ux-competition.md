## 1. 目的と問い

フロントエンド（React 19 + Vite + TypeScript）は、入力欄と出力欄のあるタブを足しただけの仮のものだった。作り直しの前に、UX 設計の土台を1つ決めたい。1つの作り手に書かせると、その作り手の癖や見落としがそのまま残る。そこで、作り手を変えて同じ課題で3案を独立に書かせ、事前に決めた基準で選ぶことにした。Aki_Ha が担当するフロントエンドの作り直し（ブランチ `dev/akiha_frontend`）の最初の段階にあたる。

知りたかったこと:

1. 3案のうち、どれを土台にするか。事前登録の規則だけで決まるか
2. 2人の審査役の判定は、どのくらい一致するか
3. 土台の案にどんな問題が残り、ほかの案の要素で解消できるか

## 2. 仮説

- 事前登録したのは、シナリオ S1〜S4、審査基準（必須 M1〜M3、指標 K1〜K4）、判定規則（順位の合計が最小の案を土台にする。同点は K2 が小さい方。ほかの案の要素は、土台の案で見つかった問題を解消する場合に限って取り込む）である。どれも応募作の依頼文に書き、応募者にも同じ文を見せた（`ux-r-prompt-gemini.txt:36-50`）。
- **どの案が勝つかの仮説は立てていない。** 期待していたことも書き残していない。
- 事前登録はリポにはコミットしていない。依頼文の控えとして vault に置いた（12節）。
- K3 を2人の審査役の平均にすること、K1・K2 の細かい数え方は、依頼文の審査基準には書いていない（9節）。

## 6. 手順

1. 監査役が依頼文を作った。P・Q は Claude Code のサブエージェントで生成した。
2. R は Codex に頼む予定だったが、ログイン切れで動かなかった。agy で Gemini 4 Argon (High) に差し替え、依頼文を道具なしの版に書き換えた（5.1）。所要 489 秒、入力 8,936 トークン、出力 36,403 トークン（うち思考 19,249）。返答の本文を `ux-r.md` にした（返答そのもの `ux-r-response.md` とバイト単位で同じ）。
3. 作者を伏せ、P・Q・R の名前で審査役に渡した。
4. **審査役 B の1回目（無効）:** 3案を1つの依頼文（121,174字。`judging-b-prompt.txt`）にまとめて渡した。入力は 53,344 トークン、所要 127 秒、終了コード 0、エラーの表示は無かった。返答の「審査の限界」に、R の後半（第4章 S3 の途中から第11章まで）が切れていたと書かれていた（`judging-b.md:124`）。R の S3 は依頼文の先頭から 75% の位置で始まるので、後ろの約25%が届かなかったと推定する。入力が黙って切られたもので、返答を読むまで気づけなかった。この回は採点に使っていない。
5. **審査役 B の2回目（有効）:** 1案ずつの3つの依頼文（`judging-b-p/q/r-prompt.txt`。43,798字・41,101字・37,980字）に分け、3つ並列で流した。入力は P 28,185・Q 29,082・R 24,782 トークン（3つの合計 82,049 は、1回目の 53,344 より多い）、所要は P 239 秒・Q 230 秒・R 136 秒。P と R の返答は、各案の終わりの方（P の 10.2 と 11.3、R の第9章）にも触れており、終わりまで届いていたと見られる。Q の返答が場所を挙げて触れたのは W13（Q の全体の約7割の位置）までで、終わりまで届いたかは返答からは確かめられない（入力のトークン数は、終わりまで届いた P とほぼ同じ）。
6. **審査役 A:** 3案を全文読み、origin/main と照らして `judging-a.md` を書いた。
7. 監査役が集計した。K3 は審査役 A と B の値の平均にし、指標ごとの順位と合計を出した。P と Q が同点で規則では決まらなかったので、審査役 A の感度分析（`judging-a.md:227-238`）を数えて Q を選んだ（事前登録に無い決め方）。
8. 実行役のサブエージェント（Opus 5.5）が、Q を土台に確定版（`docs/frontend/ux-spec.md`）を書いた。取り込みと修正は、その文書の変更履歴にある。

**再現のしかた:** 依頼文の控え（12節）を同じ作り手・審査役に渡す。agy は3節の起動方法で、依頼文を約3万トークン未満に分けて渡す。LLM の生成は毎回変わるので、同じ応募作や同じ数は出ない見込みが高い。P・Q と審査役 A の依頼文は残っていないので、正確には再現できない。

## 7. 指標の定義

| 指標 | 定義 | 判定・数え方 |
|---|---|---|
| M1（必須） | S1 で、自由記述を一度も入力せずに最初の科目提案まで到達できる | 審査役 A が「満たす／満たさない」 |
| M2（必須） | スマホ（幅 375px 想定）と PC の両方で、主要タスクの導線が定義されている | 同上 |
| M3（必須） | 提案ごとに「なぜこの科目か」と根拠（シラバスなどの出典）を確かめる導線がある | 同上 |
| K1 | S1 の最初の画面から最初の提案までの操作数（タップ・選択・入力の合計）。少ないほど良い | 審査役 A。リンクを開くことは数えない。主値は応募作が置いた前提（学科入りのリンクなど）のまま数え、前提なしの副値は採点に使わない（`judging-a.md:22-26`） |
| K2 | バックエンドに新たに求める機能の数。少ないほど良い | 審査役 A。origin/main と remote ブランチに無い項目を数えた。応募作が「進行中」とした項目も、確かめられなければ数えた。静的 JSON の書き出しもデータ側の作業なら数えた（`judging-a.md:93`）。無いときの代わりがあって中心の流れが止まらない項目は数えなかった（`judging-a.md:56, 96, 140`） |
| K3 | 審査役が Nielsen の10原則で見つけた重大度3以上の問題の数。少ないほど良い | 重大度は Nielsen の 0〜4（3 = 重大、4 = 致命的）。採点に使う値 = (審査役 A の数 + 審査役 B の数) ÷ 2 |
| K4 | S1〜S4 のうち、開始から完了まで流れが書けている数（0〜4）。多いほど良い | 審査役 A |

**順位と合計:**

- 指標ごとに、良い方から 1・2・3 の順位を付ける（K1〜K3 は小さいほど良い、K4 は大きいほど良い）。同じ値の案には、その順位の平均を付ける（2案が1位で並べば 1.5 と 1.5、3案が並べば 2・2・2）。
- 合計 = K1 の順位 + K2 の順位 + K3 の順位 + K4 の順位。必須3つを満たす案のうち、合計が最小の案を土台にする。同点は K2 が小さい方。

**計算の例（P）:** K1 = 0 は Q と並んで最良なので 1.5。K2 = 2 も Q と並んで 1.5。K3 = (0 + 7) ÷ 2 = 3.5 で Q と並び 1.5。K4 = 4 は3案とも同じなので 2。合計 = 1.5 + 1.5 + 1.5 + 2 = 6.5。R は K1 = 1・K2 = 4・K3 = (3 + 6) ÷ 2 = 4.5 がどれも最下位で 3、K4 は 2、合計 11。

各列の意味:

- **作者:** 審査のあとで明かした作り手。審査役には伏せた。
- **M1〜M3:** 審査役 A の判定。3案とも3つすべてを満たした。
- **K1:** 審査役 A の主値（7節）。P・Q は学科入りのリンクで開くと最初の提案が出ている（0回）。R はボタンを1回押す。
- **K2（厳密）:** 審査役 A の数え方（7節）。「厳密」は、応募作が「進行中」「既存のデータ」と申告した項目も、origin/main と remote ブランチで確かめられなければ数えた、という意味。内訳は 8.3。
- **K3: A / B / 平均:** 審査役 A の数、審査役 B（2回目）の数、その平均。採点には平均を使った。
- **K4:** 審査役 A の判定。3案とも S1〜S4 の4つすべて。
- **順位:** K1・K2・K3 の平均・K4 のそれぞれでの順位（同じ値は平均の順位）。
- **合計:** 4つの順位の和。小さいほど良い。

## 10. 考察

### 10.1 P と Q の同点と、事前登録外の決め方

- P と Q は、K1（0）・K2（2）・K3（A も B も同じ値）・K4（4）のすべてで同じ値だった。2案とも「入口は系統図からの決まった計算で LLM を待たせない」「LLM は自由記述だけ」という同じ骨格で、K1 と K2 はその骨格でほぼ決まる値だったため、と推定する（K2 の内訳も、学科データの用意とエージェントの関西大学データ対応という同じ2項目）。
- 感度分析の4通りの解釈は、もっともらしさも重みも同じではない。行を数えて Q を選んだのは検定の結果でなく判断で、「差がほとんど無い2案から Q を選んだ」と読むのが正確である。学科の指定なしでリンクを開く場面を重く見れば、P が上になる。
- 確定版で Q を土台にしたあと、P の要素を12取り込んだ（8.5）。P と Q の差は、確定版ではさらに小さくなっている。

### 10.2 K3 の食い違い

- 審査役 A は P・Q に 0件、R に 3件、審査役 B は P・Q に 7件、R に 6件を付けた。B はどの案にも A より多く付け、案の並びも逆になった（A では R が最も多く、B では R が最も少ない）。平均の並び（R が最下位）は A の並びと同じで、A の差（3）が B の差（1）より大きかったためである。
- **同じ系統のモデルを甘く見た可能性がある。** Claude 系の審査役 A は Claude 系が書いた P・Q を 0件とし、Gemini 系の審査役 B は Gemini 系が書いた R を最も少なくした。ただし、各セルが1回ずつで、ほかの説明とも区別できない。
- **方法の違い:** A はリポを読み、origin/main と照らした。A が R に付けた重大度3の3件のうち2件（R-3a の応答時間、R-3b の科目単位の前提）は、リポの事実と照らして初めて分かる問題である。B はリポを見ておらず、設計書の中の食い違いや書かれていないことを多く挙げた。
- **重大度の付け方の違い:** 同じ問題に、A が重大度2、B が重大度3〜4を付けた例が、有効な回の記録で少なくとも3つある。Q の待ちの結果が届いたことを知らせる手段が無い点（A の Q-2d が2、B-Q4 が3）、Q の[始める]が確認なしで前の状態を消す点（A の Q-2e が2、B-Q7 の一部として3）、P の待ちの画面から別の画面へ移ると回答を失いうる点（A の P-2d が2、B の P の問題1が4）。K3 の差の多くは、問題を見つけたかどうかより、重大度3の線をどこに引いたかの差だと考えられる。
- 以上から、K3 は審査役1人の値では土台を決められない。次に同じ形で比べるなら、各案を別系統の審査役2人以上で見て、問題ごとに突き合わせ（同じ問題か、重大度は何か）、一致の度合いも報告する。重大度の付け方を合わせる例を、審査の前に両方の審査役に示す。

### 10.3 R の事実の誤り4点

審査役 A は、R の次の4点が origin/main と食い違うと記録した（`judging-a.md:203-207`）。

1. 応答時間を「数秒程度」とした。origin/main の実験報告では、中央値 29.7 秒・32.9 秒（[ノード設計の比較](2026-10-11_node-design-comparison.md)）、1問 53〜93 秒（[test3-2 の e2e](2026-10-11_test3-2-e2e.md)）
2. 科目単位の前提関係を前提にした。関西大学の系統図の線は `CourseGroup` どうしの `PREREQUISITE_FOR` で、科目どうしの前提は無い（ADR-0016）
3. 類似度の線（`SIMILAR_TO`）がある前提にした。origin/main に無く、ADR-0016 では次フェーズ
4. 既存の対話エンドポイントが関西大学の科目について答えられる前提にした。今のエージェントはシードの構造を前提にしている

このうち 2〜4 は、R が見た依頼文の説明（「前提科目の線と、内容が似た科目の線を作る予定」「関西大学の投入はこれから」。4.1）と食い違わない。R はリポを読めない条件で書いたので、R の点数の低さは、モデルの違いだけでなく、使えた情報の違いも反映している。このコンペで比べたのは「モデル」ではなく「作り手の構成（モデル・道具・使えた情報・スキル）」である。

### 10.4 このコンペで分からないこと

設計書を審査役が読んで判定しただけで、利用者（1年生や調査の協力者）は1人も使っていない。どの案が実際に「納得して選べる」体験になるかは、このコンペでは分からない。確定版で入れた審査後の修正（9件）は、どの審査役にも見せていない。

## 11. 限界

- 応募作は3案・各1回の生成、審査役は2人・各案1回（審査役 B の無効な回を除く）。生成のばらつきは測っていない。
- 作り手の条件（モデル・道具・リポの読み取り・スキル・視点）がそろっていない（4.3、10.3）。
- 作り手と審査役のモデルが重なる（審査役 A と P・Q、審査役 B と R）。
- P・Q と審査役 A への依頼文はファイルとして残っていない。P・Q の依頼文は「R の文とほぼ同じで、リポの読み取りの許可とスキル・視点の指定がある」という監査役の記録だけが手がかり。
- K1・K2 の値は審査役 A の解釈に依存し、解釈を変えると同点が崩れる（8.4）。
- 審査役 B の1回目の入力の切れは、返答を読んで初めて分かった。2回目に切れが無かったことは、返答の引用の範囲で見ただけで、入力の全文が届いたことを直接は確かめていない。Q については、返答の引用が終わりの方に及んでおらず、引用の範囲からも確かめられない（6節の5）。
- P・Q の生成の時刻、所要時間、トークン数は記録していない。
- agy の実行ログ（トークン数・所要時間の出どころ）は作業用の一時フォルダにあり、vault には移していない（12節）。
- 設計書の評価であり、利用者でのテストではない。

## 付録: 試行錯誤の経緯

- **R の作り手の差し替え:** R は別系統の Codex に頼む予定で依頼文（`ux-r-prompt.txt` と見られる）を用意したが、Codex のログインが切れていて動かなかった。Gemini 4 Argon (High) を agy で呼ぶことにし、依頼文を道具なしの版（`ux-r-prompt-gemini.txt`）に書き換えた。
- **agy の入力形式:** 最初の試行（Gemini 4 Argon (Medium)）は、標準入力の1行に `event` の項目が無く「stream input message is missing the "event" field」で失敗した。`{"event":"user","message":{"content":"…"}}` の形で通った。
- **固定の上乗せ:** 「了解」とだけ返させる1行の依頼でも、入力は 7,137 トークンだった。依頼文のほかに約7千トークンの固定の上乗せがある。
- **審査役 B の1回目の切れ:** 3案をまとめた 121,174字の依頼文では、R の後半（全体の後ろ約25%）が黙って切れた。エラーも終了コードの異常も無く、返答の「審査の限界」の記述で気づいた。1案ずつ（入力が約2.5万〜2.9万トークン）に分けた2回目では、P と R の返答が案の終わりの方まで触れていた（Q は引用の範囲からは確かめられない。6節の5）。
