## 1. 目的と問い

論文（情報処理学会 DBS 研究会、原稿締切 11/13）の技術実験の問いは「履修相談の検索で、グラフ探索はベクトル類似度より良い結果を返すか」である。
Yuto の計画書は4つの手法（Pure Vector、Vector + Metadata、Pure Graph、Graph + Vector のハイブリッド）を比べるとしている。

駒澤のデータ（科目の Postgres 投入、前提関係、正解ラベル）はまだ揃っていない。そこでこの実験では、手元にあるシード20科目で次の3点を確かめた。

1. 4つの手法を、同じ質問の解釈（QuerySpec）・同じ採点で動かせる実験基盤ができたか
2. 指標（Recall@K、NDCG@K、前提違反など）が想定どおりに計算されるか
3. シードではどの指標が手法の差を出し、どの指標が出せないか

この実験の数字を「グラフがベクトルより良い」証拠としては使わない。理由は §4.3（正解がグラフ側に偏っている）に書く。

「差あり」の基準（検定ではなく記述上の約束）: 率の指標は、質問ごとの値の平均差の絶対値が0.10以上、かつ符号カウント
（A が上回った質問数 − B が上回った質問数）の絶対値が3以上で、向きが一致するとき。片方だけなら「差は小さい」。
件数の指標は合計の差が2以上。コストは比が1.5倍以上。

### 4.3 golden の偏り

E は Pure Graph（起点あり）と同じ Cypher の出力そのものなので、Pure Graph はほぼ満点になるように作られている。
したがって Pure Graph の満点は手法の優劣ではなく「正解の作り方」を映している。また「次に取れる」の E は3段先までの後続をすべて含むので、
別の前提科目が未履修でまだ取れない科目（例: q01 の機械学習 303 は線形代数 202 も要る）も正解に入っている。

## 5. 条件

### 5.1 共通の QuerySpec

質問ごとに1回だけ「質問の解釈」を作り、`backend/eval/specs/seed_query_specs.json` にコミットした。4条件はすべてこのファイルを読むだけにし、解釈の違いが条件の差に混ざらないようにした。

| 項目 | 作り方 | 例（q01） |
|---|---|---|
| mode・起点（anchor） | 既存の `agent.intent_rules.parse_intent`（シードの科目名・別名の辞書照合。LLM も DB も使わない） | next_step、GMS-301 データサイエンス入門 |
| 向き（direction） | next_step → forward（後続）、prereq → backward（前提）、topic → topic（共通トピック）、unclear → なし | forward |
| メタデータ条件 | 質問文から正規表現で学期・曜日・時限・単位数を取る | なし（q12 だけ「金曜・3限」） |
| 全文検索のクエリ | 質問文の Lucene 特殊文字をエスケープしたもの | `データサイエンス入門の次に取れる科目は\?` |
| 埋め込むテキスト | 質問文そのもの | |

14問すべてで、mode と起点が golden と一致した（H0 の前半）。

### 5.2 4つの検索方式

どの方式も「QuerySpec を受け取り、科目の順位リストを返す」同じ形の関数で、名前で登録してある（`backend/eval/retrievers.py`）。

```text
質問 ──(1回だけ)──> QuerySpec（mode・起点・向き・メタデータ条件・全文検索クエリ）
                        │
   ┌────────────────────┼─────────────────────┬──────────────────────────────┐
   C1 Pure Vector        C2 Vector+Metadata     C3 Pure Graph                  C4 Hybrid
   質問の埋め込み         C1 + WHERE             起点 → 固定 Cypher で展開      C1 の上位3件 → 固定 Cypher で展開
   × 20科目の埋め込み     （条件があるときだけ）   （起点が無ければ全文検索）       → C1 の順位と RRF で統合
   └────────────────────┴─────────────────────┴──────────────────────────────┘
                        │
              起点科目を除いて上位10件（共通）→ 採点（K=5, 10）
                        │
              検索系10問だけ: 上位5件 → LLM 1回で回答 → 科目表で引用を照合
```

**C1 Pure Vector**: 質問文の埋め込みと、20科目それぞれの文書の埋め込みのコサイン類似度を計算し、高い順に並べる。
文書は `title: {科目名} | text: トピック: {トピック}。{シラバス本文}`（例: `title: 情報リテラシー | text: トピック: 情報基礎。大学生活および…基礎を学びます。`）。
科目コードは文書に入れていない。近似検索（HNSW）の誤差を混ぜないよう、インデックスを使わない厳密検索にした（§6.3）。DB へのクエリは SQL 1本。

**C2 Vector + Metadata**: C1 の SQL に、QuerySpec のメタデータ条件から作った WHERE を足す（開講時期の文字列の部分一致と単位数の一致）。
条件が無い質問では C1 と同じ SQL になる。計画書は「学年・学期・必修区分」で絞るとしているが、シードに学年と必修区分の列は無い。

**C3 Pure Graph**: 起点がある質問では、起点から向きに沿って既存の固定 Cypher（`course_core.graph.traversal`）で辿る。
後続は3段先まで、前提は3段前まで、共通トピックは共有トピック数の多い順。並び順は Cypher が返す順のまま。
起点が無い質問（unclear）では、Neo4j の全文検索インデックス（科目名とトピック名、日本語を2文字ずつに区切る cjk アナライザ）に質問文を投げ、
トピックに当たったらそのトピックを扱う科目に置き換え、一致スコアの高い順に並べる（この場合は辿らない）。Cypher 1本。

**C4 Hybrid（計画書の④、構想メモの C4a）**: まず C1 の順位を作り、上位3件（m=3）を「入口」にする。各入口から、QuerySpec の向きに沿って C3 と同じ Cypher で辿る。
C1 の順位と、入口ごとの辿った結果の順位を、Reciprocal Rank Fusion（RRF）で1本にまとめる。
科目 c の点数は score(c) = Σ 1 / (60 + c の順位) で、c が現れたリストすべてについて足す（同点は科目コード順）。
向きが無い（unclear）ときは辿らず C1 の順位のまま。入口は起点ではなくベクトル検索で決めるので、起点がコードで書かれた質問（q02、q06）では入口を外しうる。SQL 1本と Cypher 3本。

**共通の後処理**: 各方式に11件まで返させ、QuerySpec の起点科目を除き（ユーザーが名前を挙げた科目は推薦ではないため）、上位10件に切る。
この後処理は4条件で同じ。各（条件, 質問）を5回流し、5回とも同じ順位になることを確かめた（すべて一致）。

### 5.3 回答生成（S1 と同じ形）

検索系10問×4条件について、上位5件を LLM に1回だけ渡して回答を書かせた。組み立ては本番の `build_compose_agent`（ツール無し、出力は answer と cited_codes）。
入力は `{"question", "intent": {mode, 起点}, "candidates": [{rank, code, title, evidence}]}` の JSON。
evidence は決定的な根拠文で、C1・C2 は「質問文とのコサイン類似度 0.735（ベクトル検索の 2 位）」、C3 は既存の静的 DAG と同じ
「GMS-303 機械学習 は GMS-301 データサイエンス入門 と前提関係で 1 段つながっています（GMS-301 → GMS-303）」、C4 はその両方。
指示文は事前登録 §3.5 に本文を凍結した（「入力 JSON の内容だけを根拠にする」「言及した科目コードはすべて cited_codes に入れる」など5項目）。
生成のあと、cited_codes を `agent.grounding.build_grounded_answer` で実験用 DB の科目表と突き合わせ、存在しないコードを数えた。

7. 生成の煙テスト（q01・C1 で1回。結果は集計に使わない）
8. `generate`: 検索系10問×4条件（40回）。条件の順は質問ごとに1つずつずらした
9. `summarize`: 集計とサマリー

途中の出来事: 最初の `setup-db` の実行中に Docker Desktop のエンジンが再起動し、何も書き込まれないまま止まった（再起動後にやり直した）。
最初の `retrieve` は、厳密検索の確認（§6.3）で止まり、何も記録していない（manifest に aborted として残してある）。

### 6.3 厳密検索の確認

ベクトル検索は、HNSW（近似）ではなく全件を比べる厳密検索で測ると事前登録した。pgvector の README にある方法（`enable_indexscan = off`）を使い、
検索の前に EXPLAIN で「HNSW インデックスを使わない計画（Seq Scan → Sort）」になることをハーネスが確かめる。
最初の実行では、接続プール（asyncpg）が接続を返すたびに `RESET ALL` を流すため、接続を作ったときの `SET` が2回目以降の取得で消え、
HNSW を使う計画になっていた。この確認で止まったので、結果を記録する前に、設定を接続の起動パラメータで渡す形に直した（79084ad）。
効果（セッション単位でインデックス走査を使わない）は事前登録どおりで、サマリーの「事前登録からの逸脱」に記録した。

## 7. 指標

記号: R = 起点を除いた順位リスト、R_K = R の上位 K 件、E = 期待科目、F = 出してはいけない科目、a = 起点科目。

| 指標 | 定義・式 | 具体例 |
|---|---|---|
| Recall@K | \|R_K ∩ E\| / \|E\|。期待科目のうち上位 K 件に入った割合 | q01 の C1 は R_5 = (401, 201, 203, 102, 302)、E = {303, 401}。入ったのは 401 だけなので Recall@5 = 1/2 = 0.50 |
| NDCG@K | DCG@K / IDCG@K。DCG@K = Σ_{i=1..K} rel_i / log2(i+1)、rel_i は i 位が E に入れば1。IDCG@K は min(\|E\|, K) 件が上から並んだときの DCG。期待科目が上位にあるほど1に近い | 同じ例で、401 が1位なので DCG = 1/log2(2) = 1。IDCG = 1 + 1/log2(3) = 1.631。NDCG@5 = 1 / 1.631 = 0.61 |
| forbidden@K | \|R_K ∩ F\| | q01 の C1 は 201（データサイエンス入門の前提科目）を出したので1 |
| 前提違反@K（「次に取れる」4問のみ） | 履修済み D = {a} ∪ a の前提科目をすべて（推移的に）たどった集合。R_K の科目で、直接の前提科目のうち1つでも D に無いものの数。違反率 = 違反数 / R_K の件数 | q01: D = {301, 201, 203, 101, 102}。C3 の R_5 = (303, 401) のうち、303 は 202 が D に無いので違反、401 は 301 だけなので違反でない。違反1件、違反率 1/2 = 0.50 |
| 履修済みの推薦（副次） | R_K のうち D − {a} に入る科目の数 | q01 の C1 は 201, 203, 102 の3件 |
| 返却件数 | R_K の件数（グラフは K 件に満たないことがある） | q04 の C3 は 303 だけで1件 |
| 所要時間 | 1回の検索の壁時計時間。5回の中央値。質問の埋め込みを作る時間（1問約0.4〜0.7秒）は含めない | |
| DB クエリ数 | 1回の検索で PostgreSQL と Neo4j に送ったクエリの数 | C4 は SQL 1 + Cypher 3 = 4 |
| 生成の指標 | C = 正規化した cited_codes、C' = C − {a}。未検証コード = C のうち DB に行が無いコード。候補外の引用 = C' のうち渡した5件に無いコード。recall = \|C' ∩ E\| / \|E\|、precision = \|C' ∩ E\| / \|C'\| | |

参考として、順位をランダムに並べたときの期待値を解析的に出した（候補数 N は起点を除いて19）。E[Recall@K] = K/N、
E[NDCG@K] = (\|E\|/N) × Σ_{i=1..K} 1/log2(i+1) / IDCG@K。

K=5 を主にした理由: 起点を除く19科目から10件を取ると、ランダムでも Recall@10 の期待値が約0.53 になり、差が縮む。K=10 は「q05 のように期待科目が6件ある問いを全部拾えるか」を見るために記述だけ出した。
K=5 では q05（\|E\|=6）の Recall@5 は最大でも 5/6 = 0.83 になる。

## 10. 考察

1. **向きのある問いでは、グラフの探索がベクトル類似度より正解に近い（H1）。** ただし正解自体がグラフの探索の出力なので、これは「グラフが正解を再現できる」ことの確認に近い。
   独立した正解（人が付けた関連度）で同じ差が出るかは、駒澤のデータで確かめる必要がある。
2. **ベクトル類似度は「向き」を区別しない。** 「データサイエンス入門の次」に対して、C1 は前提側の 201・203・102 を上位に入れ（forbidden 7件、履修済みの推薦5件）、後続の機械学習（303）は7位で上位5件に入らなかった。
   類似度は「同じ話題」を拾うが、「前か後か」は文の表面に現れないので拾えない。これはシードの小ささとは関係なく、手法の性質として論文に書ける観察である。
3. **前提違反の指標では、今のグラフ探索は良くならなかった（H5 不支持）。** 静的探索の「次」は「3段先までの後続すべて」で、「今すぐ取れる科目」ではない。
   q02 では C3 の上位5件のうち4件が、別の前提科目（例: 301 は 203 も要る）が未履修で今は取れない。golden の期待科目そのものも同じ定義で、4問の期待科目を並べると違反は10件になる（C3 の10件と同じ）。
   一方 C1 の違反が C3 より少ないのは、取れる科目を選んだからではない。C1 の上位5件には、既に履修済みの前提側の科目（4問で計5件。q01 では 201・203・102）や起点と関係の薄い科目が入り、それらは前提違反として数えられない（違反にはならないが役に立たない）。
   グラフが前提充足で有利になるには、「後続のうち、前提科目がすべて履修済みのものだけ」を返す探索（Cypher の ALL 条件1本で書ける）を条件として持つ必要がある。これは今回の4条件に無い。
4. **ハイブリッドは、入口の当たり外れに強く左右される。** C4 は向きのある問いで C1 を大きく上回った（NDCG@5 +0.30）が、入口をベクトル検索だけで決めるので、q06（コードで尋ねる問い）では入口を外して大きく崩れた。
   起点が辞書照合で確定する質問では、起点を入口に使う変形（構想メモの C4a の別形）も考えられるが、それは「ベクトルを使わない」に近づく。どちらを提案手法にするかは、起点が名前で確定しない質問（駒澤の興味ベースの質問）の比率で決まる。
5. **ベクトルは「近い分野」でも負けた（H3 不支持）。** q08〜q10 の正解は「共通トピックを持つ科目」で、トピックは Neo4j のエッジとして明示されている。文書にトピック名を入れても、類似度の順位は共通トピックの有無を再現しなかった。
   シードの本文は1文（約87字）で、類似度が0.57〜0.73 の狭い幅に集まり、差がつきにくい。本文が長い駒澤では変わりうる。
6. **回答生成では、どの条件も存在しないコードを作らなかった。** 渡す候補を決定的に作り、LLM には書くことだけを任せる形（S1）では、ハルシネーションは今回0件で、引用の質は検索部の質でほぼ決まった。
7. **シードで測れないもの**: メタデータ絞り込み（C2）の効果は q12 の1問でしか見えない。ギャップ補完（計画書の評価軸③）は外部教材のデータが無いので測れない。

## 11. 限界

- 正解（golden）は C3 と同じ固定 Cypher の出力に合わせて作られており、C3 の満点は設計上の前提である。H1・H2・H4 はこの偏りの中での結果として読む。
- シードは架空の20科目で、本文は1文。規模も文書の長さも実データと違う。
- 質問は14問（検索系10問、種類ごとに3〜4問）。各条件1回ずつで、検定はしていない。「差あり」は §2 の記述上の約束による。
- 起点の除去と向きは QuerySpec（辞書照合）から来るので、C1・C2 も起点の除去にだけは辞書照合の結果を使っている。C4 の入口はベクトル検索だけで決める。
- 文書に科目コードを入れていないので、コードで尋ねる問い（q02、q06）で C1・C4 は不利になる。入れるかどうかは駒澤で決め直す。
- 埋め込みモデル（gemini-embedding-2、1536次元）は暫定。生成の LLM は1種類で温度は API の既定値。生成は1回ずつで揺れを測っていない。
- 所要時間はローカルの Docker（Windows）での値で、駒澤の規模には外挿できない。
- unclear の4問は「聞き返す」動作を測るもので、検索部の比較には向かない（記述だけにした）。

## 13. 次にやること（駒澤のデータが揃ったら）

1. 駒澤の1学部分の科目を Postgres に入れる（Yuto の担当予定）。表が `test_postgres_syllabus` と違う形なら、`eval/corpus.py` に読み込み関数を足し、表名の定数を合わせる。

7. 事前登録を書いてから流す。

## 付録: 試行錯誤の経緯

失敗した試行も含めて、実行の順に書く。

1. Neo4j の使えるアナライザを `db.index.fulltext.listAvailableAnalyzers()` で確かめようとしたが、応答が返らなかった（cypher-shell と Python ドライバの両方。原因は未確認）。
   Neo4j 5 に組み込みの `cjk` アナライザを指定してインデックスを作り、`SHOW FULLTEXT INDEXES` で設定（`fulltext.analyzer: cjk`）と状態（ONLINE）を確かめる形に切り替えた。
2. 最初の `setup-db` は、実行中に Docker Desktop のエンジンが再起動して止まった。DB には何も書かれていなかった（拡張も表も無いことを確認）。
   エンジンの再起動で止まった backend・frontend・実験用 DB のコンテナを `docker start` で戻し、`setup-db` をやり直した。
3. 最初の `retrieve` は、厳密検索の確認（EXPLAIN）で「HNSW を使う計画」が見つかって止まった（§6.3）。検索結果は1件も記録していない。
   原因は asyncpg のプールが接続の返却時に流す `RESET ALL` で、設定を接続の起動パラメータに移して直し（79084ad）、確認は取得し直して2回行うようにした。manifest にはこの試行を aborted として残した。
4. 生成の煙テストを q01・C1 で1回流し、計測（LLM 1回、入力約540トークン）と引用の照合が動くことを確かめた。結果は集計に使っていない（manifest には LLM 1回として数えてある）。
5. 生成のサマリーで「候補外の引用」が C4 に10件出たので、生データで1件ずつ確かめ、すべて LLM に渡した根拠文（経路の表記など）に書かれたコードだと分かった。
   これをサマリーの列として機械的に出すように足した（de1104a。事前登録の指標は変えていない）。
6. Yuto のブランチのマージで、backend の起動処理が `CREATE EXTENSION vector` を実行するようになった。dev の `postgres` は pgvector を持たないので、
   このブランチでは backend の API が起動に失敗する（実験は `docker exec` で動かしたので影響なし）。dev の DB のイメージは変えていない。
