# [ADR-0006] 意図パーサと Evidence 生成の純関数設計および Golden テスト駆動開発

- **ステータス**: 提案中 (Proposed)
- **起票日**: 2026-08-18
- **決定者 / 議論の場**: akiha (@Akitoshi-Hasegawa), yuto (@cyanosome)
- **関連リンク**: Commit `3027342`, Commit `34444c6`, PR #4, `backend/agent/src/agent/intent_rules.py`, `backend/agent/src/agent/rank.py`, `backend/tests/golden/questions.json`

---

## 1. 背景と課題 (Context & Problem Statement)

- **自然言語の質問から「探索意図」と「アンカー科目」を特定する難しさ**
  - ユーザー（学生）からの自然言語による履修相談から、「前提科目を調べたいのか（`prereq`）」「次に履修すべき発展科目か（`next_step`）」「関連トピックか（`topic`）」という探索モードと、起点となる科目（アンカー）を正確に抽出する必要があった。
- **LLM のハルシネーションによるグラフ探索誤爆リスク**
  - この意図抽出を無防備に外部 LLM API（プロンプト生成）に依存させた場合、LLM は実在しないそれらしい科目コード（例: `GMS-305`）を捏造して出力する危険がある。
  - 後続の Neo4j 多段探索モジュール（`traversal.py`）がこの偽のコードを受け取ると、当然ながら検索結果は 0 件となる。
  - このとき、「本当に前提科目が存在しないのか」「LLM がコードを捏造したせいで空振りしたのか」の切り分けが不可能になり、研究における評価結論が「履修系統図に沿った検索ができなかった」という誤った判定に歪んでしまう。
- **テストの実行速度・コスト・非決定性（Flakiness）**
  - 意図解釈のテストに毎回 LLM API やデータベース接続を要求すると、テスト実行時間が大幅に遅延し、API コストが発生し、LLM の出力の揺らぎによって CI テストが不安定になる。

---

## 2. 決定の判断基準 (Decision Drivers)

- **決定論性と再現性**: 同一の質問文に対して、何度実行しても 100% 同じ意図解析・根拠文生成結果が得られること。
- **ハルシネーションの構造的遮断**: グラフデータベースに対して実在しない科目コードが渡る事故をアーキテクチャ境界として完全に防ぐこと。
- **超高速・軽量なテストループ**: 外部 DB や LLM API に依存せず、CI やローカル環境でミリ秒単位でテストを完走できること。
- **ルールの保守性・運用の明快さ**: 意図判定が外れた際、辞書やキーワード表に 1 単語追加するだけで修正・チューニングできること。

---

## 3. 検討した選択肢 (Considered Options)

1. **選択肢 A: LLM に質問文を渡し、直接科目コードや Cypher クエリを出力させる方式（End-to-End LLM）**
   - プロンプトで「前提科目を探す Cypher を出力してください」と指示し、LLM の生成したクエリをそのまま実行する。
2. **選択肢 B: 意図パーサと Evidence 生成を「純関数（Pure Function）」として分離し、Golden テスト（14問）で駆動する方式 【採用案】**
   - 意図解釈とアンカー特定を DB や LLM に一切触らない決定論的ルール（純関数）として実装。
   - LLM には科目コードを直接出力させず、自然言語の語（`anchor_term`）までしか扱わせない制約を課す。
   - 事前に定義した 14 問のゴールデンテストセット（`questions.json`）で挙動を完全検証する。

---

## 4. 決定事項と選定理由 (Decision & Rationale)

**採用**: **選択肢 B: 純関数による意図パーサ・Evidence 生成 ＋ Golden テスト駆動**

### 1. 「LLM に科目コードを直接出力させてはならない」という設計原則の確立
- グラフ探索の入力となる科目コード（`GMS-\d{3}`）への解決は、必ずローカルの辞書（`seed/courses.json`）または Postgres の ILIKE 検索（`resolve_anchor`）という **決定論的モジュール** を介して行う契約とした。
- これにより、LLM のハルシネーションがグラフ探索層を破壊するリスクを構造的に排除した。

### 2. 純関数としての意図パーサ設計 (`intent_rules.py`)
- `parse_intent` は DB にも LLM にも触らない純関数（Pure Function）として設計。
- 以下の 3 段構えで決定論的に処理：
  1. テキスト正規化（全角半角・空白・記号処理）
  2. モードキーワード表の最長一致検索（`prereq`, `next_step`, `topic`）
  3. 科目名・略称辞書との照合によるアンカー特定
- 意図を外した質問があった場合でも、出力される `matched_rule` を確認し、キーワード表に 1 語追加するだけで安全に運用修正できる体制を整えた。

### 3. Evidence（根拠文）の決定論的生成 (`rank.py`)
- 探索結果からユーザーへ提示する根拠文（Evidence）を、テンプレートに基づいて決定論的に生成。
- どのエッジを辿ったのかの軌跡（`traversed_edges`）を正確に記録し、後段の Agent が説明文を構築する確実なエビデンスを提供する。

### 4. Golden テストセットによる品質保証 (`questions.json`)
- 実験 3-2 設計書（§8.1）に基づき、代表的な 14 問のゴールデン質問（前提質問、発展質問、トピック質問、曖昧な質問、スコープ外の質問等）を定義。
- DB や LLM を立ち上げることなく、テストスイート（A1）において 14 問すべてが期待通りの意図・アンカーとして解析されることを 100% 検証可能にした。

## 5. 各選択肢の評価 (Pros & Cons)

### 選択肢 A: End-to-End LLM 生成方式
- **メリット (+)**:
  - 柔軟な言い回しや口語表現に対してプロンプトだけで対応できる可能性がある。
- **デメリット・見送り理由 (-)**:
  - 科目コードのハルシネーションが発生し、探索 0 件の原因が特定できなくなる。
  - テストの実行に時間とコストがかかり、出力の非決定性により CI が不安定化する。

### 選択肢 B: 純関数パーサ ＋ Golden テスト駆動 【採用案】
- **メリット (+)**:
  - 実行時間が数ミリ秒であり、CI で瞬時に 100% 再現可能なテストが回せる。
  - 不正なコードが Neo4j に渡る事故を水際で完全に防止できる。
  - ルール追加や修正がキーワード表の編集のみで安全に行える。
- **デメリット・受容するリスク (-)**:
  - キーワード表に登録されていない未知の言い回しに対しては、初期状態でアンカーまたはモードが `unclear`（曖昧）として判定される（※ただし、曖昧と正しく判定して聞き返す方が、ハルシネーションで嘘をつくよりシステムとして健全である）。

## 6. 影響と結果 (Consequences)

- **良い影響 (Positive)**:
  - コミット `3027342`（PR #4）により、意図パーサ・Evidence 生成の全ロジックが DB/LLM 不要の純関数として完成した。
  - コミット `34444c6` において、CI（GitHub Actions）の backend ジョブに 1 行追加するだけで、Golden 14 問テストが毎コミット数秒で自動検証されるようになった。
  - 後続のステップ 5（Workflow 通電）において、ノード間のデータ契約（`SearchIntent`, `CandidateSet`, `AnswerPayload`）が強固に安定した。
- **今後の展望（LLM とのハイブリッド化方針）**:
  - より複雑な自然言語表現を解釈するために将来 LLM をパーサに導入する場合であっても、本決定で確立した **「LLM には自然言語の語（anchor_term）までを出力させ、科目コードの確定は決定論的パーサに委ねる」** 防壁ルールを厳格に維持する。
