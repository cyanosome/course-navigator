# [ADR-0023] PostgreSQL Web管理ツールとしてのAdminerの導入

- **ステータス**: 承認済 (Accepted)
- **起票日**: 2026-10-25
- **決定者 / 議論の場**: インフラ・開発環境検討
- **関連リンク**: コミット `b58623c`, `47bf040`, `d52203d`, `db/compose.yaml`, [ADR-0001](0001-use-traefik-and-gateway-network.md), [ADR-0002](0002-use-polyglot-persistence-postgres-and-neo4j.md)

---

## 1. 背景と課題 (Context & Problem Statement)

- 本プロジェクトでは、シラバス詳細データ、大学要覧要件、科目区分、検証用メタデータなどを PostgreSQL に格納して運用している（[ADR-0002](0002-use-polyglot-persistence-postgres-and-neo4j.md)）。
- Ingestion の実行結果確認、データ投入パイプラインのデバッグ、テーブルスキーマの確認、および SQL クエリの検証において、ブラウザからアクセス可能な Web 管理インターフェースが必要であった。
- 本システムをデプロイする研究室サーバー環境には、利用可能なドメイン・サブドメインが固定されており、任意のサブドメイン（例: `db.example.com` 等）を個別に追加できないインフラ制約が存在する。
- したがって、Traefik v3 リバースプロキシ（[ADR-0001](0001-use-traefik-and-gateway-network.md)）配下において、単一ホスト名に対するパスベースルーティング（サブパス `/adminer`）でセッションおよび Cookie が動作し、リソース消費の少ないデータベース管理ツールの選定が必要であった。

## 2. 決定の判断基準 (Decision Drivers)

- **パスベースルーティング（`/adminer`）への適合性**: 固定サブドメイン制約下において、サブパス配下でリダイレクトループや Cookie パス不整合を起こさず動作すること。
- **メモリ消費量とリソース効率**: Docker コンテナのメモリ消費量が小さく（10〜30MB程度）、共有サーバー環境への負荷が軽微であること。
- **設定手順の簡素さ**: 専用のメタデータDBや複雑な初期設定を必要とせず、Docker Compose 起動直後から PostgreSQL への接続・テーブル操作・SQL実行が可能であること。

## 3. 検討した選択肢 (Considered Options)

1. **選択肢 A (採用案)**: **Adminer（公式Dockerイメージ `adminer:latest`）の採用**
   - 単一のPHPスクリプトで動作する軽量なデータベース管理Webツール。
   - `db/compose.yaml` にサービスを追加し、Traefik のミドルウェア（`StripPrefix` および `RedirectRegex` による末尾スラッシュ補正）を適用して `http://<host>/adminer` で運用。
2. **選択肢 B**: **NocoDB の採用**
   - スマートスプレッドシート形式でデータを閲覧・編集できるGUIツール。
   - 当初 `db/compose.yaml` に統合を試行（コミット `b58623c`）。
3. **選択肢 C**: **pgAdmin 4**
   - PostgreSQL 公式の多機能 Web 管理ツール。
4. **選択肢 D**: **Web GUI を導入せず、ローカルデスクトップGUI（DBeaver 等）や CLI（psql）のみに限定**
   - Web コンテナは追加せず、ポートフォワード経由で各自のローカルクライアントから接続する。

## 4. 決定事項と選定理由 (Decision & Rationale)

**採用**: **選択肢 A: Adminer（公式Dockerイメージ `adminer:latest`）の採用**

### 選定理由
- **パスベースルーティングでの動作実績**: Adminer は Traefik の `RedirectRegex`（末尾スラッシュ付与）および `StripPrefix` ミドルウェアを設定することで、固定サブドメイン環境下のサブパス（`/adminer/`）でセッションおよび Cookie を維持して動作した（コミット `d52203d`）。
- **リソース効率**: Adminer コンテナのメモリ使用量は約 10〜30MB であり、起動時間は 1秒未満である。
- **単一コンテナでの完結**: 内部で別のメタデータデータベースを保持する必要がなく、単一コンテナで完結するため、環境構築手順が少ない。
- **選択肢 B (NocoDB) を見送った理由**:
  - 当初導入を試みたが、NocoDB はルートパス（`/`）でのホスティングを前提とした内部リダイレクトや静的アセット解決を行う仕様となっていた。
  - 研究室サーバーのサブドメイン固定制約により独立したサブドメインを割り当てられず、サブパス運用を試みたが、リダイレクトループおよび Cookie パスの不整合が発生したため採用を見送った（コミット `47bf040` にて Adminer に置換）。
- **選択肢 C (pgAdmin 4) を見送った理由**: コンテナサイズが数百MB以上、メモリ消費も数百MB〜1GBに達し、シラバスデータの確認用途に対してリソース消費が過大であるため。
- **選択肢 D を見送った理由**: 参画メンバーが個別に GUI ツールをインストール・接続設定する工数を省き、ブラウザ経由で同一のDB確認環境を利用できるようにするため。

## 5. 各選択肢の評価 (Pros & Cons)

### 選択肢 A: Adminer の採用（採用案）
- **メリット (+)**:
  - Traefik ミドルウェアとの組み合わせにより、パスベースルーティング（`/adminer`）で動作する。
  - メモリ消費が約10〜30MBに収まる。
  - テーブル閲覧、レコード編集、DDL確認、SQL実行など開発に必要な機能を備える。
  - 追加のメタデータDBを必要としない。
- **デメリット・受容するリスク (-)**:
  - 画面UIはシンプルな構成となっている。
  - プロキシサブパス運用の仕様上、末尾スラッシュの有無（`/adminer` vs `/adminer/`）によるセッション不整合を防ぐため、Traefik ミドルウェアでリダイレクトを明示する必要がある。

### 選択肢 B: NocoDB の採用（見送り案）
- **メリット (+)**:
  - スプレッドシート形式のUIで非エンジニアにとってもデータの視認性が高い。
- **デメリット・見送り理由 (-)**:
  - サブドメインが固定されたサーバー環境において、サブパス配下でのリダイレクト処理および Cookie 管理が整合せず、アクセスエラーが発生した。
  - NocoDB 自体のメタデータ管理用データベースの定義が必要となり、コンテナ構成が増加する。

### 選択肢 C: pgAdmin 4（見送り案）
- **メリット (+)**:
  - クエリプランの可視化や統計グラフ等の詳細機能を備える。
- **デメリット・見送り理由 (-)**:
  - メモリ消費およびコンテナサイズが大きく、共有開発サーバーでの常時起動に適さない。

### 選択肢 D: ローカルクライアント限定（見送り案）
- **メリット (+)**:
  - サーバー側のコンテナリソースを消費しない。
- **デメリット・見送り理由 (-)**:
  - 各開発環境でのクライアント導入・接続設定の手順が発生する。

## 6. 影響と結果 (Consequences)

- **良い影響 (Positive)**:
  - `db/compose.yaml` に `adminer` サービスが統合され、Traefik 経由（`http://<host>/adminer/`）でブラウザから PostgreSQL のテーブル（`courses`, `graduation_requirements` 等）を確認できるようになった。
  - 研究室サーバーのサブドメイン固定制約を満たしつつ、安全なパスベースでの外部アクセスが確立された。
  - Ingestion パイプラインの開発およびデータ投入の検証工程が効率化された。
- **留意点・トレードオフ (Negative / Neutral)**:
  - Traefik 設定において `TrailingSlash` リダイレクトミドルウェアの維持が必要となる。
