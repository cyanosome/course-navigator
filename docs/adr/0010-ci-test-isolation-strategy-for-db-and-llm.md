# [ADR-0010] CI（GitHub Actions）における DB / LLM 依存テストの分離実行戦略

- **ステータス**: 提案中 (Proposed)
- **起票日**: 2026-08-24
- **決定者 / 議論の場**: akiha (@Akitoshi-Hasegawa), yuto (@cyanosome)
- **関連リンク**: Commit `34444c6`, Commit `a63ce68`, `.github/workflows/ci.yml`, `backend/agent/pyproject.toml`, `backend/agent/tests/fake_graph.py`

---

## 1. 背景と課題 (Context & Problem Statement)

- **テスト種類の多層化とボトルネックの顕在化**:
  - `backend/agent` パッケージ（意図パーサ、Evidence生成、ADK Workflow等）の開発に伴い、テストケースの性質が以下の3層に分化してきた。
    1. **純粋なロジックテスト（決定論的・高速）**: 形態素・ルール判定（Golden 14問テスト: A1/A10）や、スタブを用いたワークフロー疎通テスト（A5/A6）。
    2. **実データベース（Neo4j / PostgreSQL）依存テスト**: グラフ多段探索の再現性やCypherクエリ実体検証（A4: `test_reproducibility`）。
    3. **実 LLM（Gemini API 等）依存テスト**: 回答生成プロンプトやモデル推論を含むエンドツーエンドの挙動検証。
- **CI 実行時の制約と課題**:
  - GitHub Actions 上の CI において全テストを一括実行しようとすると、以下の問題が生じる。
    - **フィードバック速度の低下**: Neo4j / PostgreSQL サービスコンテナの起動待ちとデータ初期化により、PRごとのCI完了時間（目標: 1〜2分以内）を大幅に超過する。
    - **外部 API 依存と Flaky テスト**: 実 LLM を CI で呼び出すと、API 利用料金が発生するだけでなく、ネットワーク遅延・レートリミット・確率的出力によるテスト落ち（Flaky tests）を招く。
    - **シークレット管理と権限境界**: フォーク元からの PR やセキュリティ制約下で API キーを参照できない場合がある。

---

## 2. 決定の判断基準 (Decision Drivers)

- **CI 実行速度（高速なフィードバックサイクル）**: PR 作成・更新時に 1〜2 分以内で Lint・型チェック・ユニットテストが完走すること。
- **決定論性と再現性（Flaky の排除）**: 外部ネットワーク障害や確率的推論に依存せず、常に 100% 同一の結果を返すこと。
- **コストゼロ**: CI の実行に伴い外部 LLM API の従量課金を発生させないこと。
- **開発者体験（ローカルでの実行性）**: Docker を起動していない環境でも、手元の pytest コマンドでコアロジックの回帰テストが即座に行えること。

---

## 3. 検討した選択肢 (Considered Options)

1. **選択肢 A: 毎回 Docker サービスコンテナを起動し、全結合テストを実行する**
   - CI 上で PostgreSQL / Neo4j コンテナを立ち上げ、シードデータを投入した上で全テストを実行する。
2. **選択肢 B: 実 LLM / 実 DB の呼び出しを都度コード内の if 文や環境変数で分岐する**
   - 各テスト関数内で環境変数（CI=true 等）を判定してスキップ処理（pytest.skip）を個別記述する。
3. **選択肢 C: pytest カスタムマーカー（`-m "not db and not llm"`）とテストダブル（インメモリスタブ）による分離実行 【採用案】**
   - `pyproject.toml` に `db` および `llm` マーカーを正式登録し、CI では純関数およびインメモリスタブ（`fake_graph.py`）のみを実行対象とする。

---

## 4. 決定事項と選定理由 (Decision & Rationale)

**採用**: **選択肢 C: pytest カスタムマーカー（`-m "not db and not llm"`）とテストダブル（インメモリスタブ）による分離実行**

### 選定理由
- **関心事の明確な分離**: テストコード内にベタ書きの環境分岐を入れず、pytest 標準のメタデータ（マーカー）で宣言的にフィルタリングできる。
- **高速化の達成**: DB 起動・データ投入および外部 API 通信を全廃することで、CI 上でのテスト実行時間が数十秒で完走する。
- **多分岐・合流ロジックの検証性確保**: 実 DB を使わない代わりに `fake_graph.py`（`courses.json` から静的探索結果を返すインメモリスタブ）を DI することで、ワークフローの DAG 構造（A5/A6）を CI 上で完全に網羅検証できる。

### 具体的な実装内容
1. **pytest マーカーの明示的定義 (`backend/agent/pyproject.toml`)**:
   ```toml
   [tool.pytest.ini_options]
   markers = [
       "db: 実 Neo4j / PostgreSQL が要るテスト（CI では -m 'not db' で除外する）",
       "llm: 実 LLM API が要るテスト（CI では -m 'not llm' で除外する）",
   ]
   ```
2. **CI 実行コマンドの指定 (`.github/workflows/ci.yml`)**:
   ```yaml
   - run: uv run pytest tests -q -m "not db and not llm"
   ```
3. **テストの役割分担**:
   - **CI 対象 (高速・常時実行)**: A1（Golden 14問）、A5/A6（スタブ結合）、A10（純関数 Evidence 検証）
   - **CI 除外 (ローカル / 結合環境限定)**: A4（`test_reproducibility`、実 Neo4j 依存）および将来の実 LLM 結合テスト

---

## 5. 各選択肢の評価 (Pros & Cons)

### 選択肢 A: 毎回 Docker サービスコンテナを起動し、全結合テストを実行する
- **メリット (+)**:
  - Cypher クエリの構文や実スキーマとの不整合を CI で即座に検知できる。
- **デメリット・見送り理由 (-)**:
  - CI 実行時間が数分に延び、開発サイクルが著しく低下する。Neo4j のメモリ消費により GitHub Actions ランナーの枯渇リスクがある。

### 選択肢 B: 実 LLM / 実 DB の呼び出しを都度コード内の if 文や環境変数で分岐する
- **メリット (+)**:
  - pytest の設定を拡張しなくても個別制御できる。
- **デメリット・見送り理由 (-)**:
  - テスト関数ごとにボイラープレートな条件判定が散落し、保守性が著しく損なわれる。

### 選択肢 C: pytest カスタムマーカーとテストダブルによる分離実行 【採用案】
- **メリット (+)**:
  - pytest のエコシステムに準拠し、`@pytest.mark.db` / `@pytest.mark.llm` のデコレータ1行で属性を付与できる。
  - CI は 1分以内で決定論的に完走し、API 利用料も発生しない。
- **デメリット・受容するリスク (-)**:
  - 新規テスト作成時にマーカーを付け忘れると、CI 上で接続エラー（`ConnectionRefusedError`）を起こすリスクがある。
  - 実 DB とのスキーマ不整合を CI 単体では検知できない。

---

## 6. 影響と結果 (Consequences)

- **良い影響 (Positive)**:
  - PR 作成から 1 分程度で CI の合否判定が完了し、迅速なマージ・デプロイが可能となった。
  - 開発者が外出先やノート PC など、Docker デーモンを立ち上げていない軽量な環境でも `pytest -m "not db and not llm"` で即座にリグレッションテストを実行できる。
- **留意点・トレードオフ (Negative / Neutral)**:
  - CI 単体では実 DB との結合保証が得られないため、スキーマ変更時やリリース前には手元で `pytest -m db` を明示的に実行する必要がある。
  - 将来的な nightly ビルド（夜間に実コンテナを起動して結合テストを全走させる別ワークフロー）の構築をタスクとして考慮する。
- **次のアクション (Next Actions)**:
  - `backend/tests` 配下のテストファイルに対し、実 Neo4j を呼ぶテストには `@pytest.mark.db`、実 LLM を呼ぶテストには `@pytest.mark.llm` を漏れなく付与する。
