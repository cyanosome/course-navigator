# [ADR-0020] 大学要覧PDFスプリットによる卒業要件・必修区分のハイブリッドモデリング

## 1. 背景と課題 (Context & Problem Statement)

- 関西大学のシラバスHTML（1,029科目）および履修系統図ベクターPDFの取り込み（Phase 3.0）により、科目の詳細情報とDAGグラフの構築が完了した。
- 履修支援AIが卒業要件を満たす履修計画を策定するためには、**「各科目の必修・選択必修・自由選択の別」** および **「学部・学科の卒業要件（全学共通科目の必要単位数、専門必修科目の必要単位数等）」** のカリキュラム制約情報が必要である。
- これらの卒業要件や科目区分ルールはシラバス本文には記載されておらず、「大学要覧（履修要項）PDF（`all_page.pdf`）」の配当表に記載されている。
- 全学部の要覧が結合されたPDFから該当学部（環境都市工学部等）の情報を抽出し、PostgreSQLでの集計・外部キー制約検証と、Neo4jでのグラフ推論の両方に適合するデータパイプラインを設計する必要があった。

## 2. 決定の判断基準 (Decision Drivers)

- **決定論的な抽出処理**: 卒業要件や必修区分について、確率的な推論ではなく、ルールベースで再現可能な抽出が行えること。
- **学部別の分割処理**: 全学部結合PDFから特定学部のページ群を抽出し、学部単位で独立してパース・検証できること。
- **Polyglot Persistence の役割分担**:
  - PostgreSQL: 単位数の総和集計、外部キー制約、整合性検証用。
  - Neo4j: 科目ノードと要件ノード間のリレーション（`[:FULFILLS]`、`[:REQUIRES]`）によるグラフ探索用。

## 3. 検討した選択肢 (Considered Options)

1. **選択肢 A (採用案)**: **大学要覧PDFスプリット ＋ ルールベースパーサー ＋ Postgres & Neo4j ハイブリッドローダー**
   - `pdfplumber` を用いて要覧PDF（`all_page.pdf`）から特定学部の該当ページ群をページ番号指定でスプリット抽出。
   - 表構造解析により、科目別区分（必修/選択必修/選択）と卒業要件（カテゴリ・必要単位数）を構造化JSONへ変換。
   - PostgreSQL（`graduation_requirements`, `course_requirements`）に投入してクロス集計・整合性検証を行い、Neo4j（`RequirementGroup`, `Requirement` ノード、`[:FULFILLS]` エッジ）へオントロジーとして展開。
2. **選択肢 B**: **シラバス概要テキストからの LLM ゼロショット推論**
   - シラバスの備考欄や授業概要から、LLM を用いて必修/選択の区分を推論させる。
3. **選択肢 C**: **Neo4j 単一保持（RDB 非格納）**
   - 卒業要件データをグラフオントロジーとしてのみ保持し、単位数の整合性集計も Cypher のみで行う。

## 4. 決定事項と選定理由 (Decision & Rationale)

**採用**: **選択肢 A: 大学要覧PDFスプリット ＋ ルールベースパーサー ＋ Postgres & Neo4j ハイブリッドローダー**

### 選定理由

- **再現性の確保**: PDFの表レイアウト座標に基づき、決定論的パーサー（`requirement_parser.py`）でパースすることで、LLMの推論ばらつきを排除したデータ抽出が行える。
- **Postgres による計算検証**: 要覧に記載された総卒業要件単位数の内訳が、抽出した各カテゴリの必要単位数の合計と一致するかを、PostgreSQL の SQL 集計・検証CLI（`verify_requirements.py`）で機械的に検算できる。
- **グラフ探索モデルの構築**: 検証済みのデータを Neo4j にロードし、`(:Course)-[:FULFILLS]->(:Requirement)-[:BELONGS_TO]->(:RequirementGroup)` という関係を構築することで、LLM Agent が「未充足の要件を満たす科目群」を単一のCypherクエリで取得可能になる。

## 5. 各選択肢の評価 (Pros & Cons)

### 選択肢 A: PDFスプリット・ルールベースパーサー・ハイブリッド格納（採用案）

- **メリット (+)**:
  - ルールに基づく抽出のため、入力が同一であれば同一の出力が得られる。
  - 学部ごとにページ範囲を指定して処理を分離できるため、他学部展開時も同一の抽出フレームワークを適用可能。
  - Postgres での集計検算と Neo4j でのパス探索の双方を利用可能。
- **デメリット・受容するリスク (-)**:
  - 要覧PDFのレイアウトや表組が改訂された場合、パーサーの座標・正規表現ルールの見直しが必要となる。

### 選択肢 B: LLM ゼロショット推論（見送り案）

- **メリット (+)**:
  - パーサーの初期実装コード量が少ない。
- **デメリット・見送り理由 (-)**:
  - シラバス本文中に全体の卒業要件枠組みに関する記述が含まれておらず、推論に必要な情報が不足する。誤判定のリスクがある。

### 選択肢 C: Neo4j 単一保持（見送り案）

- **メリット (+)**:
  - データ投入先が1箇所で済む。
- **デメリット・見送り理由 (-)**:
  - 単位数の集計検算や外部キー制約の検証をCypherのみで行う構成は、リレーショナルDBと比較して集計クエリの記述と検証の工程が増える。

## 6. 影響と結果 (Consequences)

- **良い影響 (Positive)**:
  - `ingestion/src/transformers/kansai/handbook_splitter.py` および `requirement_parser.py` により、環境都市工学部の要覧から必修・選択必修区分と卒業要件が抽出された。
  - PostgreSQL スキーマに `graduation_requirements` テーブル群が追加され、`verify_requirements` CLI によりシラバス1,029科目との突合検証が完了した。
  - Neo4j 上で科目ノードと要件ノードが結ばれ、卒業要件を考慮した履修推薦の推論基盤が確立した。
- **留意点・トレードオフ (Negative / Neutral)**:
  - 他大学・他学部への展開にあたっては、各大学の要覧PDFのフォーマットに合わせたパーサー設定が必要となる。
- **次のアクション (Next Actions)**:
  - Phase 3.7 の 3モード探索エンジン（[ADR-0018](0018-neo4j-cypher-three-mode-search-engine-and-api-contract.md)）において、卒業要件を満たす科目のフィルタ条件として活用。
